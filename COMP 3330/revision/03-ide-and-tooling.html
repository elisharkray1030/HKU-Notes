IDEs and tooling

What Android Studio actually is, what the SDK versions on a project screen mean, how code becomes an installable APK, and what the alternative toolkits (React Native, Cordova, Flutter, Unity, App Inventor) each are. This is the vocabulary of every later tutorial.

What an IDE does for you

You cannot write programs on a phone (the lecture concedes you might on a tablet), so development happens on a computer. An IDE (Integrated Development Environment) is a program that lets you develop software for a platform on a PC; normally it bundles a source editor, a compiler and/or interpreter, and a debugger. When everything is fine, you transfer the app to the phone. Sometimes an SDK for a specific device model is required.

The lecture's tool lists: for Android, AIDE, App Inventor, DroidScript, CppDroid, Android Web Developer, Python/Java suites, Eclipse, Arduino, Visual Studio, Unreal Engine, Android Studio, Corona, PhoneGap and more; for iOS, Xcode, AppCode, Atom, SublimeText 3, CodeRunner 2. The two that matter in this course: Eclipse (the historical Android IDE, Java only) and Android Studio (Java and Kotlin: the slides describe Kotlin as "aiming at simplifying Java syntax"). For iOS there is Xcode (Objective-C / Swift), which runs only on macOS; the lecture lists cloud Mac services (MacInCloud and friends, with academic pricing) for students without a Mac.

Inside Android Studio: SDK, AVD, emulator

Google ships one all-in-one developer tool, and Tutorial 1 names its parts: Android SDK Tools, Android Platform-tools, the latest Android platform, and the latest Android system image for the emulator. The mental model:

An Android Virtual Device (AVD) is a configuration defining the characteristics of an Android phone, tablet, Android Wear or Android TV device that you want to simulate in the Android Emulator. The AVD Manager (Tools > Device Manager, or its icon) creates and manages them via "Add a new device → Create Virtual Device". The lecture's warning is practical: different virtual devices place different CPU and memory requirements on your computer.

The four SDK versions, once and for all

Module settings (right-click "app" → "Open Module Settings") hold four numbers that students confuse for a year running. The lecture's definitions:

  • Compile SDK version: that SDK version is used for compilation.
  • Build Tools version: that version of build tools is used for building the APK.
  • Min SDK version: your user needs that SDK version or above to install and run your app.
  • Target SDK version: your app is targeted at that SDK version; if the user runs that version, performance is optimal.
Exam angle

One-liner: compile is about your build machine, min is about your users' floor, target is the behaviour contract you opt into. A question "a user on API 24 tries to install an app with min SDK 26: what happens?" has exactly one right answer: they cannot install it.

On real devices: Android recognises signed APK files by default, so tapping any signed APK installs it. For development, connect by USB; the phone then appears as a run target alongside emulators, once "Developer options" is turned on (the lecture links Samsung's steps as the example).

Hands-on: the tutorial's own flow

Tutorial 1's path is the skeleton of every project in this course: launch Android Studio → new project → "Empty Views Activity" for "Phone and Tablet" → application name, package name, language Kotlin, minimum SDK (e.g. API 26). The project then holds a layout file (activity_main.xml) and a main program whose onCreate() calls setContentView(R.layout.activity_main) to inflate the layout. Gradle is the build system driving compilation and packaging: the course notes (Chapter 0) that Gradle packages native C/C++ libraries into the APK (built with CMake and called through JNI), and Tutorial 1 has you set the build tools version used for building the APK. Third-party libraries go in app/libs and are attached with "Add As Library" : you will do exactly that with JEP in the Card 24 project.

The worked example is a BMI calculator (BMI = weight in kg divided by height in m squared). Three steps worth re-typing into muscle memory: declare fields for the widgets, bind them in onCreate() with findViewById, and give the button a handler. The tutorial wires the handler through the XML onClick attribute ("calc") instead of a listener.

Kotlin
class MainActivity : AppCompatActivity() {
    private var height: EditText? = null
    private var weight: EditText? = null
    private var result: TextView? = null

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        height = findViewById<EditText>(R.id.editText1)
        weight = findViewById<EditText>(R.id.editText2)
        result = findViewById<TextView>(R.id.textView)
    }

    fun calc(v: View?) {
        val h = height!!.text.toString().toFloat()
        val w = weight!!.text.toString().toFloat()
        val bmi = w / h / h
        result!!.text = "Your BMI is: $bmi"
    }
}
Java
public class MainActivity extends AppCompatActivity {
    private EditText height, weight;
    private TextView result;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_main);
        height = findViewById(R.id.editText1);
        weight = findViewById(R.id.editText2);
        result = findViewById(R.id.textView);
    }

    // bound to the button via the XML android:onClick="calc" attribute
    public void calc(View v) {
        float h = Float.parseFloat(height.getText().toString());
        float w = Float.parseFloat(weight.getText().toString());
        float bmi = w / h / h;
        result.setText("Your BMI is: " + bmi);
    }
}

Read that as three facts, not thirty lines: views are declared as fields and found by resource id; the string in an EditText must be converted to a number before arithmetic; and "$bmi" is string interpolation (page 5 covers the syntax). The layout work is Tutorial 1's step "drag a LinearLayout (vertical), two Plain Text fields, one button, one TextView into it and name them": page 4 explains what those names are doing.

Tip

Submission mechanics are part of the tooling story too: File → Export → Export to Zip File is how you package a project, and the course accepts that as proof of tutorial work.

The cross-platform tools, sorted by idea

Chapter 3 surveys many tools; they collapse into four ideas. Learn the idea and the names stick.

  1. Native UI, other language. React Native (Facebook): build cross-platform apps with only JavaScript, using the same design as React for web applications and composing UI from declarative components. The claim from the slides: you build a real mobile app indistinguishable from one built in Objective-C / Swift / Java / Kotlin, because React Native uses the same fundamental UI building blocks as regular iOS and Android apps: you assemble them with JavaScript and React.
  2. Own UI, own renderer. Flutter (Google, introduced May 2017): an open-source SDK for Android and iOS whose engine, written mainly in C++, renders with Google's Skia graphics library and interfaces with the platform SDKs. Apps are written in Dart. Page 7 covers it hands-on.
  3. Web page in a box. Apache Cordova: an open-source framework using standard web technologies (HTML5, CSS3, JavaScript) for cross-platform development. Applications execute within wrappers targeted to each platform and rely on standards-compliant API bindings to reach device capabilities (sensors, data, network status). This is the hybrid app of page 1, with the toolkit named.
  4. Game engines. A game engine is a framework for making video games: main game program (the game logic), rendering engine (2D/3D display), audio engine, physics engine, and AI usually factored into a specialist module. Unity (Tuanjie in China and HKSAR; C#) and Unreal (C++) target web plugins, desktop and mobile. Cocos Creator is an open-source 2D/3D graphics engine and content platform scripting in JavaScript and TypeScript.

The frame concept explains why engines exist: the UI is updated frame by frame (the whole screen), with all updates made in a buffer first and then copied to the screen as one complete frame. The time axis is divided into frames updated at predefined intervals, like a cinema movie; any change goes into the next frame. That buffer-then-swap is what keeps animation smooth when several components update at once.

Mini Programs (WeChat Mini Program, launched end of 2016; Alipay and Baidu equivalents) are the lecture's newest category: obtained by searching inside another app, scanning a QR code, or opening a shared link; tiny memory and storage, no installation, quick to open, with a user experience closer to a native app. Structurally the slides call them hybrid apps: a native container at the bottom layer, and WXML, WXS and JS (developed from HTML and CSS) on top for business development: similar to a browser and server-side architecture. WeChat DevTools is the development environment.

Discuss

Take a position: a client wants one codebase for iOS and Android, a heavily custom visual design, and a smooth animated UI. Argue for exactly one of React Native, Flutter or Unity, using the lecture's own descriptions of each. Evidence that would change your mind: the client hires a team fluent in only one of the three languages involved (JS/TS, Dart, C#).

MIT App Inventor: the visual programming route

Chapter 3A exists as a research pointer, and the slides say outright: "You are not supposed to use App Inventor in this course." It still shows up in exam discussions of programming education, so know what it is.

A visual programming language (VPL) lets programmers code graphically: the IDE provides graphical elements (spatial texts, nodes, icons) that users assemble to program. The advantage the lecture gives: young children find complicated syntax hard, so a VPL lets them understand what a program is and basic programming logic. It is a research direction in the programming community (the slides cite Choi et al. 2013 and Fields et al. 2013).

App Inventor for Android is an open-source web application, originally from Google and now maintained by MIT. Its interface, similar to Scratch and StarLogo TNG, lets users drag-and-drop visual objects to create an Android app; it is widely used by Hong Kong primary and junior secondary students. The working area has four panes: Palette (materials for making your application), Viewer (how the application looks on the phone screen), Components (all components including hidden ones) and Properties (each selected component's settings). The Blocks editor offers Control, Logic, Math, Text, Colors, Variables and Procedures blocks, and only correctly shaped blocks combine: that snap-together constraint is the type system made visible.

The lecture's button-and-label walkthrough is a full pipeline in miniature: drop a Button and a Label in the Viewer, set FontSize/Height/Width/Text in Properties, snap "when Button1.Click" together with "set Label1.Text to" and a "Hello" text block, then Build → Android App (.apk) and install via USB transfer or QR code. The phone blocks installation by default until you allow apps outside the Play Store: the same open-distribution story as page 2.

Compare

App Inventor produces an APK like Android Studio does, but expresses logic as blocks instead of text. Same lifecycle, same distribution, different notation: which is exactly why it is cited as an easy-to-learn IDE research direction.

Check yourself

Q1

A student sets min SDK 26 and target SDK 33. A user on Android 7.0 (API 24) tries to install the app. What does the lecture's rule say?

Min SDK version is the user's floor: "your user needs that Sdk version or above to install and run your app." Target SDK is about optimal behaviour on matching devices, and compile SDK is purely about building.

Q2

Which description matches Apache Cordova in the lecture?

That is the slide definition of Cordova. The middle option is a game engine (Unity/Unreal/Cocos territory), the last is App Inventor.

Q3

In the game-engine frame concept, why are updates made in a buffer first?

"All updates are made in a buffer first and then contents of the buffer are copied to the screen (a complete frame)... the frame concept can ensure smooth animation" because a game updates several components at once.
