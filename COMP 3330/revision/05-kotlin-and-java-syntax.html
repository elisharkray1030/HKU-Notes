Kotlin and Java syntax

Chapter 5 assumes you know Java and teaches the Kotlin the course code is written in. Learn it as a set of correspondences: every Kotlin construct on this page is a shorter spelling of a Java construct you already recognise: and the null-safety rules, which are the one genuinely new idea.

The mental model: Java with the boilerplate removed

The course's own framing (Chapter 0): Kotlin is "a variation of Java and is intended to simplify the use of Java", and Chapter 5's slides close with "if you can remember Kotlin syntax well, a Kotlin program can be much shorter than its Java counterpart". So do not learn two languages. Learn the mapping: where Java writes a keyword, Kotlin writes punctuation; where Java repeats a type, Kotlin infers it; where Java permits null and crashes at run time, Kotlin makes you decide at compile time. Tutorials use Kotlin, so Kotlin is primary here, with the Java shape always one tab away.

Source: COMP3330_Ch05_Syntax.pdf, slides 2-28; COMP3330_Ch00_CourseInfo.pdf, slide 3.

Types

Java has 8 primitive types, each with a wrapper class: boolean/Boolean, char/Character (16 bits, 0 to 65535), byte/Byte (8 bits, -128 to 127), short/Short (16 bits, -32768 to 32767), int/Integer (32 bits, about -2.1 billion to 2.1 billion), long/Long (64 bits), float/Float (32 bits) and double/Double (64 bits). Kotlin's source-level types are Boolean, Char, Byte, Short, Int, Long, Float, Double, String: same bit depths and ranges, but spelled as classes rather than primitives.

Pitfall

The slide says "Kotlin doesn't have primitive types. It uses classes as an object wrapper for primitives." True at the level you write code: everything is an object. The durable detail underneath: on the JVM, the Kotlin compiler still uses real primitives where possible, so you lose neither speed nor memory. Answer with the slide's wording in the exam; know the engine detail for your own sanity.

Source: COMP3330_Ch05_Syntax.pdf, slides 3-4.

Functions

The signature moves: the keyword fun, colon notation for parameter types and return type, and no semicolons. Three spellings of the same function, all equivalent:

Kotlin
public fun sum(a: Int, b: Int): Int {
    return a + b
}

public fun sum(a: Int, b: Int): Int = a + b

public fun sum(a: Int, b: Int) = a + b

The third form drops the return type entirely: Kotlin infers it. A function with no return value has no return type at all (the void function fun calculate(num1: Int, num2: Int, num3: Int) { ... }).

Kotlin
fun sum(a: Int, b: Int): Int {
    return a + b
}
Java
public int sum(int a, int b) {
    return a + b;
}

Default values and named arguments

Kotlin parameters may carry default values, and call sites may name their arguments. Both are impossible in Java without method overloading:

Kotlin
fun calculate(num1: Int, num2: Int = 2, num3: Int = 4) {
    …
}
calculate(1, 3)            // num2 = 3, num3 = default 4
calculate(1, num2 = 3)     // num3 = default 4
calculate(1, num3 = 5)     // num2 = default 2

The lecture's challenge (how to provide the 1st and 3rd parameters while missing the 2nd) has a one-line answer, exactly the third call: calculate(1, num3 = 5). Parameter names can be used in calls, which is also how you skip a defaulted parameter.

Kotlin
calculate(1, num3 = 5)   // num2 gets its default 2
Java
// Java has no defaults or named args: write overloads instead.
static void calculate(int num1)                  { calculate(num1, 2, 4); }
static void calculate(int num1, int num2)        { calculate(num1, num2, 4); }
static void calculate(int num1, int num2, int num3) { … }

calculate(1, 2, 5);   // skipping num2's default must be spelled out

Variables: val and var

Kotlin
val a: Int = 1            // immutable version 1: explicit type
val b: String = "tim"
var a: Int = 1            // mutable version 1
var b: String = "tim"

val a = 1                 // immutable version 2: inferred type is Int
val b = "tim"             // inferred type is String
var a = 1                 // mutable, inferred type is Int
Java
int a = 1;
String b = "tim";
final int a = 1;          // Java's closest match to val

val means the reference cannot be reassigned: value re-assignment to a and b above is a compile error. The slides describe val properties as "read-only". Type inference decides the type from the initialiser, so val a = 1 is an Int without anyone writing Int. Rule: reach for val first, use var when the value must change.

Source: COMP3330_Ch05_Syntax.pdf, slides 5-10.

Arrays and collections

Java arrays: int[] num = {1, 2, 3, 4}; or allocate then fill (num = new int[4]; num[0] = 1; ...). Kotlin builds them with functions:

Kotlin
val num = arrayOf(1, 2, 3, 4)        // implicit type declaration
val num = arrayOf<Int>(1, 2, 3, 4)   // explicit type declaration

for (i in 0..num.size-1) {
    print(" " + num[i])
}

// Array is a class: the constructor takes a size and a function from index to value
val num = Array(3, {i-> i*1})
// equivalent to val num = arrayOf(0, 1, 2)

Two creation idioms (factory function arrayOf, constructor Array(size) { index -> value }) and one traversal idiom (for (i in 0..num.size-1): the .. builds an inclusive range). The constructor's second parameter is a function: {i -> i*1} maps each index to its initial value, so indices 0, 1, 2 produce 0, 1, 2.

Q1

What does Array(3, {i-> i*1}) hold?

The slide states it is equivalent to arrayOf(0, 1, 2): size 3, and the function maps index i to i*1, so index 0 gives 0, index 1 gives 1, index 2 gives 2.

Source: COMP3330_Ch05_Syntax.pdf, slides 11-12.

Null safety: the one genuinely new idea

The type system distinguishes references that can hold null (nullable) from those that cannot (non-null). A regular String cannot hold null; str = null is a compile error. Put ? after the type to allow null: var str: String? = "hku".

Kotlin
var s1: String = "hku"
val l = s1.length            // safe: s1 is non-null, no NPE possible

var s2: String? = "hku"
val l = s2.length            // error: variable 's2' can be null

val l = if (s2 != null) s2.length else null   // handle both options
val l = s2?.length           // safe call: l is null if s2 is null; type Int?

The safe call ?. is the workhorse. From the lecture's examples: println(b?.length) on a null b prints null; a?.length on non-null a is an unnecessary safe call (the compiler says so) and prints 8 for "Computer". Note the type rule: expressions like a?.length and b?.length have type Int?: a safe call always yields a nullable result.

Safe calls chain: tim?.department?.head?.name returns null if any property in the chain is null. The lecture's side-by-side sells the point:

Kotlin
fun getZipCode(user: User?): ZipCode? {
    return user?.address?.zipCode
}
// or, with inferred return type:
fun getZipCode(user: User?) = user?.address?.zipCode
Java
public ZipCode getZipCode(User user) {
    if (user != null) {
        if (user.address != null) {
            return user.address.zipCode;
        }
    }
    return null;
}
Why it matters

Null Pointer Exceptions are a compile error in Kotlin wherever the type is non-null. The ? on variables like private var height: EditText? = null (Tutorial 1) is not decoration: it says "may not be bound yet", and the !! you see in tutorial code is the author asserting non-null, throwing at run time if wrong. Prefer ?. unless the assertion is genuinely guaranteed.

Source: COMP3330_Ch05_Syntax.pdf, slides 13-18.

String interpolation

$ embeds variables in a string literal. The lecture's three equivalent toString() versions show the compression:

Kotlin
override fun toString(): String {
    return "Song{id=" + id + ", title='" + title + "', author='" + author + "'}"
}
override fun toString(): String {
    return "Song{id=$id, title='$title', author='$author'}"
}
override fun toString() = "Song{id=$id, title='$title', author='$author'}"
Java
@Override
public String toString() {
    return "Song{id=" + id + ", title='" + title + "', author='" + author + "'}";
}

This is also what powers lines like result!!.text = "Your BMI is: $bmi" in the BMI calculator.

Source: COMP3330_Ch05_Syntax.pdf, slide 19.

Classes and objects

A Kotlin class can declare its properties and primary constructor in one header. There is no new keyword: instantiation looks like a constructor call. Note the default parameter value doing Java's overloading job:

Kotlin
class Person constructor(val name: String, val age: Int? = null)
// or simply:
class Person(val name: String, val age: Int? = null)
// name and age are read-only here

val person1 = Person("Sam", 20)
val person2 = Person("Priscilla")   // age is assigned null value
Java
class Person {
    final String name;
    final Integer age;
    public Person(String name) {
        this.name = name;
        this.age = null;
    }
    public Person(String name, Integer age) {
        this.name = name;
        this.age = age;
    }
}

Person person1 = new Person("Sam", 20);
Person person2 = new Person("Priscilla");

The Java side needs two constructors and field declarations; the Kotlin side is one line. The slides add: like Java, the compiler generates a no-argument constructor on the JVM for this shape, instantiating with default values.

Initialization. You cannot put code in the primary constructor; use an init block, which runs after the primary constructor and can access class fields:

Kotlin
class Person(val name: String, val age: Int? = null) {
    init {
        println("Hello, I'm $name")
    }
}
val person1 = Person("Sam", 20)   // prints: Hello, I'm Sam

Secondary constructors are prefixed with constructor and can delegate to the primary one with this:

Kotlin
class Car(val id: String, val type: String) {
    constructor(id: String) : this(id, "unknown")
}
val car1 = Car("1", "BYD")
val car2 = Car("2", "Isuzu")

// a class with no primary constructor: assign fields in the secondary one
class Car {
    val id: String
    val type: String
    constructor(id: String, type: String) {
        this.id = id
        this.type = type
    }
}

(The slides note a trailing comma is allowed when declaring class properties.)

Inheritance

Two rules change everything: classes are final by default, so a class must be marked open (or abstract) to be inherited from; and overriding a method requires the override keyword (plus the method being open or abstract in the parent). A subclass passes arguments to the superclass's primary constructor in its header:

Kotlin
open class Polygon {
    open fun draw() {
        // some default polygon drawing method
    }
}

abstract class WildShape : Polygon() {
    // classes that inherit WildShape must provide their own draw
    abstract override fun draw()
}

abstract class Polygon2 {
    abstract fun draw()
}
class Rectangle : Polygon2() {
    override fun draw() {
        // draw the rectangle
    }
}

class Employee(name: String, val salary: Int) : Person(name)
// passes name to Person's primary constructor, adds salary
Java
class Polygon {
    void draw() { … }
}

abstract class WildShape extends Polygon {
    @Override
    abstract void draw();
}

abstract class Polygon2 {
    abstract void draw();
}
class Rectangle extends Polygon2 {
    @Override
    void draw() { /* draw the rectangle */ }
}

class Employee extends Person {
    final int salary;
    Employee(String name, int salary) {
        super(name);
        this.salary = salary;
    }
}

Java classes are inheritable by default (which is why extends needs no permission); Kotlin makes inheritance opt-in with open. Both spell the contract the same way: abstract methods force subclasses to provide implementations.

Discuss

Take a position: the slides' claim that "a Kotlin program can be much shorter than its Java counterpart" is a maintenance win for a 1-5 person group project, not merely a typing win. Argue with the Person example and the null-safety example as evidence. Evidence that would change your mind: data showing bugs that stem from Kotlin's brevity itself: inferred types or !! assertions hiding errors that Java's verbosity would have forced into the open.

Listeners and callbacks, in this syntax

The course's Java prerequisite covers interfaces and anonymous classes; Kotlin turns them into lambdas. A listener is just an object whose method the system calls later: a callback. Both languages attach one to a button (Chapter 4 example):

Kotlin
val listener = View.OnClickListener {
    edit_text1.setText(random!!.nextInt(100).toString())
}
button1.setOnClickListener(listener)

// or inline, as the Card 24 code does:
cards[0].setOnClickListener { clickCard(0) }
left!!.setOnClickListener { expression.append("(") }
Java
Button.OnClickListener listener = new Button.OnClickListener() {
    public void onClick(View dummy) {
        edit_text1.setText(String.valueOf(random.nextInt(100)));
    }
};
button1.setOnClickListener(listener);

The Kotlin { ... } after OnClickListener or setOnClickListener is the onClick method: the parameter it receives is the clicked View. When you read cards[0].setOnClickListener { clickCard(0) }, translate it as: "when card 0 is clicked, call clickCard(0)". That single translation habit makes the whole tutorial codebase readable.

Source: COMP3330_Ch04_Layout.pdf, slides 9-10; COMP3330_Tutorial3.pdf, slides 9-11.

Check yourself

Q2

With fun calculate(num1: Int, num2: Int = 2, num3: Int = 4), what values do num2 and num3 take in calculate(1, num3 = 5)?

This is the lecture's own challenge and answer: parameter names may be used in calls, so num3 = 5 is bound by name and num2 falls back to its default 2.

Q3

Given var s2: String? = null, what is the type of s2?.length?

"The type of expressions a?.length and b?.length is Int?". The safe call returns null when the receiver is null, so the result type must admit null.

Q4

Why does class Employee(name: String, val salary: Int) : Person(name) compile only if Person is declared a certain way?

The slide's note: "All classes in Kotlin are final by default. We need to add the open keyword so that we can inherit from our Person class."
