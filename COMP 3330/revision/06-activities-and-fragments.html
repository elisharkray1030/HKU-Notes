Activities and fragments

Chapter 6 is where Android stops being XML and starts being a system that calls your code. The three ideas to own: the activity lifecycle and its ordering rules, the intent as a message between components, and the fragment as reusable screen furniture with a back stack behind it.

What an activity is

The lecture's simple understanding: an activity is a page in the foreground : the unit of UI the user is looking at. "Only one activity can be in the foreground at any time." A full application can also contain three other component types:

  • Activity: user interface / foreground (buttons, lists).
  • Service: no user interface / background (music, download).
  • Content provider: data manager (files, database).
  • Broadcast receiver: responsible for system-wide events (shut down, low battery, download complete).

The worked example on the slide: your app displays something; the user taps a button; the camera activity (another app) captures; the result feeds an email compose activity; send. Activities cross app boundaries, which is why intents exist.

The slide's own note explains why focus is separate from visibility: "an activity can be visible but not in focus if the phone screen can display multiple activities at the same time." So visible-but-not-focused is a real state, and onPause (lose focus) can fire while the activity is still on screen.

Ordering when one activity starts another

Activity A starts Activity B. The lecture's exact sequence:

  1. A's onPause() executes.
  2. B's onCreate(), onStart(), and onResume() execute in sequence. (B now has user focus.)
  3. If A is no longer visible on screen, its onStop() executes.

And the exam's favourite consequence, stated on the same slide: if A needs to write to a DB before B starts, use onPause(), not onStop(), because onPause is the last callback guaranteed to run before B is up.

Discuss

Take a position: onPause is the only callback a developer should ever use for saving state, and onStop/onDestroy are for freeing resources only. Evidence that would change your mind: the ordering rule itself: onPause runs before B is up, but if your save is slow, doing it in onPause delays B's appearance, so a lazy save in onStop plus defensive saves elsewhere might be better.

Intents: messages between components

Android intents can be imagined as messages between activities (also services and receivers). An Intent object carries an action (e.g. "start movie", "get photo") and data (e.g. movie title). Two verbs: startActivity fires the intent and forgets it; startActivityForResult fires it and expects a call-back intent with data (the slide's example: ask the camera app for a photo, receive the photo).

Pitfall

The slides print "Deprecated" over the startActivityForResult flow. The durable truth: startActivityForResult was deprecated in favour of the Activity Result APIs (registerForActivityResult). The idea in the exam is unchanged: call a component and get an intent back: only the API spelling moved on.

Explicit vs. implicit

Kotlin
// Explicit: names the component to switch to (within your app)
val intent = Intent(this, FooActivity::class.java)
startActivity(intent)

// Implicit: names only the action; the system picks the component
val intent = Intent(Intent.ACTION_VIEW, Uri.parse(urlString))
startActivity(intent)
Java
// Explicit
Intent intent = new Intent(this, FooActivity.class);
startActivity(intent);

// Implicit
Intent intent = new Intent(Intent.ACTION_VIEW, Uri.parse(urlString));
startActivity(intent);

Explicit intents are used within the application itself, one activity switching to another. Implicit intents do not directly specify the Android component to call: they specify only the action to be performed, and the system picks the component. In practice: explicit intents do your page switching; implicit intents reach outside (open a URL, capture a photo).

Intent filters

For implicit intents only. Android determines the best activity, service or receivers by comparing the contents of the Intent object to intent filters: structures associated with components that can potentially receive intents. Filters advertise a component's capabilities and delimit the intents it can handle. The rule that trips people up: a component without any intent filters can receive only explicit intents; a component with filters can receive both explicit and implicit.

XML (AndroidManifest.xml)
<activity android:name="hkucs.sample.Activity2">
    <intent-filter>
        <action android:name="android.intent.action.VIEW" />
        <action android:name="hkucs.myintentfilter" />
        <category android:name="android.intent.category.DEFAULT" />
    </intent-filter>
</activity>

Matching in the lecture's walkthrough: val i = Intent("hkucs.myintentfilter", Uri.parse("http://www.hku.hk")) then startActivity(i): the system looks for an intent filter advertising the action "hkucs.myintentfilter" (the slide says "intent filter named", but the string is the action inside the intent) and invokes Activity2, which contains this filter. The launched activity collects the URL with intent.data (Java: getIntent().getData()), holding it in a proper data structure (val url: Uri? = intent.data) and using it anywhere, e.g. label.text = url.toString().

The full example manifest shows the two filter shapes you must recognise:

  • The launcher activity's filter: action "android.intent.action.MAIN" with category "android.intent.category.LAUNCHER". An activity having this intent filter becomes the first activity, loaded when the app starts.
  • CustomActivity's filter: actions VIEW and "hkucs.intentfilter.LAUNCH", category DEFAULT, and <data android:scheme="http" /> constraining the data to http URLs. So the button sending the LAUNCH action reaches CustomActivity while the plain ACTION_VIEW button reaches the browser.
Exam angle

Filter-matching questions are step-by-step: does the intent carry an action the filter lists? a category the filter declares? data matching the filter's scheme? One mismatch and the component is not a candidate. The custom action "hkucs.intentfilter.LAUNCH" only matches because the filter advertises that exact string.

Explicit intents in practice: switching pages

The lecture's key steps: create a new layout for the new activity; define the new activity in the manifest file; in the calling activity, create a new Intent instance and start it; in the called activity, create another Intent instance to return. The code: the caller does Intent(this, MainActivity2::class.java) plus startActivity(myIntent); the manifest lists both activities, with only the first carrying the MAIN/LAUNCHER filter.

Pitfall

Look closely at the "return" step in the sample code: MainActivity2's button creates Intent(this, MainActivity::class.java) and calls startActivity: that starts a new instance of MainActivity on top, it does not go back. Real back navigation in Android is the system Back button popping the stack of activities (the same back-stack idea the fragment section below makes explicit). If a question asks what that button actually does, the honest answer is "starts MainActivity again", not "returns".

Extras and Bundles

To pass data with an intent, attach extras: key-value pairs carried inside the intent and read out as a Bundle. Sender and receiver:

Kotlin
// Sender
val myIntent = Intent(this, MainActivity2::class.java)
myIntent.putExtra("ID", 6999)
startActivity(myIntent)

// Receiver
val bundle: Bundle? = intent.extras
bundle?.let {
    bundle.apply {
        val id: Int? = getInt("ID")   // 6999; use the getter matching the type put
    }
}
Java
// Sender
Intent myIntent = new Intent(this, MainActivity2.class);
myIntent.putExtra("ID", 6999);
startActivity(myIntent);

// Receiver
Bundle bundle = getIntent().getExtras();
if (bundle != null) {
    int id = bundle.getInt("ID");   // 6999
}

Typed getters exist for the common cases: getString("ID"), getInt("ID") if the ID is an integer, getLong("ID") for a long. Arrays and objects pass too: putExtra("IntArrayList", arrayListOf(1,2,3)) and getIntArrayList("IntArrayList"); getStringArrayList likewise; and a Calendar goes over as getSerializable("Calendar").

Pitfall

The receiver slide on the printout shows getString("ID") with the comment "id = 6999" for an int that was put with putExtra("ID", 6999): and the same slide then says "Can use getInt("ID") if ID is an integer". The getter must match the type that was put; getInt("ID") is the correct pairing here. Exam answer: match getters to putters.

Serialization, from the lecture's definition: the conversion of an object to a series of bytes so it can be saved to persistent storage, streamed across a communication link, or moved between virtual machines. The byte stream can then be deserialized: converted into a replica of the original object. That is how objects like Calendar can travel inside a Bundle.

Fragments

A Fragment represents a behavior or a portion of user interface in a FragmentActivity. You can combine multiple fragments in a single activity to build a multi-pane UI, and reuse a fragment in multiple activities. The lecture's analogy: a fragment is like a modular section of an activity, a "sub-activity", with its own lifecycle, its own input events, that you can add or remove while the activity is running.

Fragment callbacks you implement

  • onCreate(): called when creating the fragment; initialize essential components you want to retain when the fragment is paused or stopped and then resumed.
  • onCreateView(): called when it is time for the fragment to draw its user interface for the first time. This is where the layout is inflated.
  • onPause(): the first indication that the user is leaving the fragment.

Basic steps

  1. Modify the layout to include one or more regions for the fragments.
  2. For each fragment: create a layout; create a class extending Fragment and implement the essential methods.
  3. In the main activity, at the place you want the fragment, run a fragment transaction.
  4. To put the fragment on the back stack, call addToBackStack as part of the transaction.
Kotlin
val manager: FragmentManager = supportFragmentManager
val ft: FragmentTransaction = manager.beginTransaction()
if (addToBackStack) {
    ft.addToBackStack(tag)                 // remember this transaction for Back
}
if (fragment != null) {
    ft.replace(R.id.frame_container, fragment, tag)  // region id, fragment, tag
}
ft.commitAllowingStateLoss()
Java
FragmentManager manager = getSupportFragmentManager();
FragmentTransaction ft = manager.beginTransaction();
ft.replace(R.id.frame_container, new FragmentOne(), "one"); // region id, fragment, tag
ft.addToBackStack("one");
ft.commitAllowingStateLoss();

Read a transaction as a staged edit: beginTransaction() opens it, replace(containerId, fragment, tag) describes swapping the fragment into a region of the activity's layout, addToBackStack(tag) records it so the Back button can reverse it (returning to whatever fragment was showing before), and commitAllowingStateLoss() applies it. The lecture's complete example wires two text areas: tapping "Fragment 1" runs addFragment(FragmentOne(), false, "one") and "Fragment 2" runs the same for FragmentTwo, both replacing into R.id.frame_container: a FrameLayout region in activity_main.xml.

The fragment class itself is small. Its one real job is onCreateView: inflate the layout and return it.

Kotlin
class FragmentOne : Fragment() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
    }

    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        // Inflate the layout for this fragment
        return inflater.inflate(R.layout.fragment_fragment_one, container, false)
    }
}
Why it matters

Fragments exist for reuse and multi-pane UIs: one fragment class embedded in several activities, or several fragments side by side on a tablet. If a screen is only ever one whole page in one app, an activity is simpler: which is why Card 24 (page 7) is one activity with no fragments at all.

Check yourself

Q1

A starts B. Which is the first callback to execute?

The ordering rule: "1. A's onPause() method executes. 2. B's onCreate(), onStart(), and onResume() execute in sequence. 3. If A is no longer visible, its onStop() executes."

Q2

A component's manifest entry has no intent-filter at all. What can it receive?

"If a component does not have any intent filters, it can receive only explicit intents. A component with filters can receive both explicit and implicit intents."

Q3

Where should an activity write to a database to be sure the write happens before the next activity appears?

The slide's explicit advice: "if A needs to write to a DB before B starts, use onPause() instead of onStop()". onStop may run only after B is up (and never if A stays visible); onDestroy is not guaranteed at all.
