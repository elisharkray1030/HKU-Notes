Practice: app lifecycle

Two lifecycles sit under this topic: the one your project lives through (Chapter 2) and the one your activity lives through on the phone (Chapter 6, at story depth here). This page drills both, because exam questions mix them on purpose.

Background: App lifecycle.

Quiz: phases, maturity and distribution

Q1

Which is the correct order of the 5 major phases of the mobile app development lifecycle?

Chapter 2 lists the phases exactly so: Inception, Design, Development, Stabilization / Testing, Deployment. Design (UX then UI) precedes development, and stabilization is a phase of its own, not an afterthought of deployment.

Q2

Your build has most functionality complete and lightly tested and bug-fixed, but you know of a few major issues. Which stage is it?

The lecture's definitions: Prototype = proof of concept, only core or partial functionality working, major bugs present. Alpha = core functionality generally code-complete but not fully tested, major bugs still present. Beta = most functionality complete with at least light testing and bug fixing; major known issues may still be present. Release candidate = everything complete and tested. "Lightly tested and bug-fixed" is the Beta marker.

Q3

Which statement about Android application signing matches the lecture?

Chapter 2: all Android applications must be signed before distribution; developers sign with their own certificate protected by a private key; a development certificate can be signed by a recognised CA but most developers self-sign; the main purpose of certificates is to differentiate between different developers and applications. Devices are not locked to a single store.

Q4

Activity A starts Activity B. Which statement is correct?

Chapter 6's coordination example: A.onPause() executes, then B.onCreate(), onStart(), onResume() in sequence (B has user focus), and if A is no longer visible its onStop() executes. Only one activity can be in the foreground at any time, though A may stay visible without focus.

Source: COMP3330_Ch02_Lifecycle.pdf, slides 2, 12, 15; COMP3330_Ch06_Activity_Fragment.pdf, slides 5, 8.

Exercise 1: which maturity stage is this build?

Exercise 1 skill: classifying prototype / alpha / beta / release candidate medium

A team shows you their shuttle-tracking app. The tracking screen works end to end but only that screen exists; two other planned features are not built at all, and the app crashes when the network drops. Later the same week, they show a build where every planned feature is implemented, none of it has been tested beyond compiling, and the crash is still there. Classify each build against Chapter 2's four maturity stages, and say which single phrase in the definitions decided each call.

Step 1: compare build 1 against the definitions

Build 1 has one working part and major bugs, with other parts missing. "Prototype: the app is still in proof-of-concept phase and only core functionality, or specific parts of the application are working. Major bugs are present." One screen working out of several is "specific parts". So build 1 is a prototype.

Step 2: compare build 2 against the definitions

Build 2 has all features implemented but untested, with major bugs remaining. "Alpha: core functionality is generally code-complete (built, but not fully tested). Major bugs are still present, outlying functionality may still not be present." Everything being built but untested is exactly "code-complete, not fully tested". So build 2 is alpha.

Step 3: rule out beta and release candidate

Beta requires "at least light testing and bug fixing", and build 2 has no testing at all, so it cannot be beta. Release candidate requires all functionality complete and tested: plainly not.

Full answer

Build 1: prototype, decided by "only core functionality, or specific parts of the application are working" plus major bugs present. Build 2: alpha, decided by "code-complete (built, but not fully tested)" with major bugs still present. Beta is excluded because no testing or bug fixing has happened yet; release candidate is excluded twice over.

Trap

The naive move is to call build 1 "alpha" because it has real working functionality, and build 2 "beta" because it has all the features. The lecture separates the stages by testing and bug fixing, not by feature count: feature completeness only distinguishes alpha from the outlying-functionality-missing case within alpha; the jump to beta is marked by light testing and bug fixing having happened.

Source: COMP3330_Ch02_Lifecycle.pdf, slide 12 (prototype, alpha, beta, release candidate).

Exercise 2: asking the inception questions

Exercise 2 skill: mapping product facts onto the inception framework medium

An HKU department wants "RoomFinder": it shows live room occupancy so students can find free classrooms. There are three rival timetable apps already, but none shows live occupancy; the university already runs a central room-booking system the app can read; students will use it while walking between buildings; and the phone's GPS could suggest the nearest free room. Map each fact to the correct inception question from Chapter 2 (competitive advantage, infrastructure integration, value, form / mobility), then name the two artefacts the lecture says help design functionality.

Step 1: label the facts

Three rival apps exist → competitive advantage ("are there similar apps? if so, how does this application differentiate?"). Central booking system already runs → infrastructure integration ("for apps distributed in an enterprise, what existing infrastructure will it integrate with or extend?"). Live occupancy solves the student's actual problem → value ("what value does this app bring users? how will they use it?"). GPS suggesting the nearest free room while walking → form / mobility ("how can I add value using mobile technologies such as location awareness, the camera, etc.?").

Step 2: write the differentiation statement

Live occupancy is the differentiator against timetable-only rivals. That is the answer to competitive advantage, not a repeat of "value".

Step 3: the two artefacts

Chapter 2 says that to help design the functionality it is useful to define actors (roles within the application, often users) and use cases (actions or intents). For RoomFinder: actors include the student and the room-booking system; a use case is "locate a free room near me".

Full answer

Competitive advantage: three rivals exist; differentiate with live occupancy data. Infrastructure integration: the existing central room-booking system. Value: students find free rooms without walking floors; used between buildings. Form / mobility: GPS to suggest the nearest free room. Artefacts: actors and use cases (student, booking system; "locate a free room near me").

Trap

It is easy to file GPS under "value" because it sounds valuable. The lecture puts mobile-technology questions (location awareness, camera) under Form / Mobility; Value is about what the app brings users and how they use it, whatever the technology. The exam expects the fact filed under the question the lecture names.

Source: COMP3330_Ch02_Lifecycle.pdf, slides 3-4 (inception).

Exercise 3: a distribution plan that survives scrutiny

Exercise 3 skill: choosing deployment routes per platform hard

A company is shipping an internal logistics app. On iOS it must reach 40 company-owned test devices now, and it will never appear on the App Store. On Android, the same build must be installable from the company's own website, not just Google Play. Write the deployment plan per platform using Chapter 2's named options, and state what signing is required on each side.

Step 1: iOS options

Chapter 2 names three: Ad-Hoc Deployment (development and testing, a limited number of properly provisioned devices), In-House Deployment (internal distribution of corporate applications not available publicly via the App Store), and the Apple App Store. "Never on the App Store" and "corporate" point to In-House; the 40 test devices today could be served by Ad-Hoc, but the enduring requirement is In-House. State both and pick In-House for the product, Ad-Hoc for the current test phase.

Step 2: Android options

Chapter 2: Android takes an open approach; devices are not locked to a single approved store, anyone may create an app store, and most Android phones allow installs from third-party stores. Installing from the company website is therefore allowed. The requirement that stands is signing: all Android applications must be signed before distribution, with the developer's own certificate protected by a private key.

Step 3: certificates

iOS has named certificate types (iPhone Developer for development runs, iPhone Distribution for testing on designated devices or store submission). Android: most developers self-sign; a CA signature is possible but not required. The purpose of certificates is to differentiate developers and applications.

Full answer

iOS: Ad-Hoc Deployment for the current 40 provisioned test devices; In-House Deployment for the corporate product, since it is internal and will never be on the App Store; sign with the iOS Distribution certificate type for device distribution. Android: distribute the signed APK from the company site (Android permits third-party distribution); sign with your own certificate protected by a private key; self-signing is normal. Certificates exist to tell developers and applications apart.

Trap

Two traps. First, "Android needs a certificate from a recognised authority": the lecture says a development certificate can be signed by a recognised CA but most developers self-sign, so a CA is not required. Second, answering "Ad-Hoc" alone for iOS: ad-hoc is for development and testing; the permanent internal distribution answer the lecture gives is In-House.

Source: COMP3330_Ch02_Lifecycle.pdf, slides 13-15 (distribution, certificates).

Exercise 4: the activity lifecycle at story depth

Exercise 4 skill: predicting callback order when one activity starts another medium

A note app has Activity A (the list of notes) and Activity B (the editor). A holds an unsaved draft in memory that must be written to the database before B can run, because B reloads everything from the database. The user taps a note in A and B opens full screen. Write the callback sequence from the tap until B has focus, name the callback where the draft write belongs, and say what is different if the phone shows A and B side by side so A stays visible.

Step 1: name what the user did and what the system does

Starting B is an activity switch. Chapter 6's coordination example: A.onPause() executes first, then B.onCreate(), onStart(), onResume() in sequence, and then A.onStop() if A is no longer visible.

Step 2: place the draft write

The write must happen before B runs, and onPause() is the only callback of A's that is guaranteed to run before B's creation. The lecture states the conclusion directly: "if A needs to write to a DB before B starts, use onPause() instead of onStop()".

Step 3: handle the side-by-side case

The lecture notes an activity can be visible but not in focus when the screen shows multiple activities. If A stays visible, its onStop() does not run; the sequence stops after A.onPause() and B's three callbacks. The draft write is safe either way, because it lives in onPause().

Full answer

Sequence: A.onPause() → B.onCreate() → B.onStart() → B.onResume() (B has focus) → A.onStop() only if A is no longer visible. The draft write goes in A.onPause(). Side by side: A is visible without focus, so A.onStop() does not fire, but the write already happened in onPause().

Trap

The naive order puts A.onStop() before B.onCreate(), because "A must be finished before B starts". Wrong: A only loses focus first (onPause), B comes up completely, and A stops afterwards if it ended up invisible. If you moved the write to onStop(), B could load stale data in the side-by-side case where onStop() never runs.

Tip

Full callback ordering, state saving and intent routing are drilled in Activities and fragments. Here the exam wants the story: one foreground activity, pause before the next is created, stop when invisible.

Source: COMP3330_Ch06_Activity_Fragment.pdf, slides 5-8 (activity concept and coordination). Treated at story depth here; details belong to Chapter 6.

Mixed exercise: from idea to store

Exercise 5 skill: running a scenario through inception, maturity and distribution hard

This one pulls in Chapter 1 (mHealth, constraints) and Chapter 2 together. A team builds "MediMinder" for elderly users: medication reminders with a one-tap "taken" button. Current state: the reminder screen works, the "taken" button crashes, and the settings screen is not built. The team wants to hand the build to 20 elderly volunteers next week, and afterwards publish to everyone. (1) Name the maturity stage. (2) Which Chapter 2 inception question did they most likely skip if volunteers abandon the app, and which Chapter 1 constraint explains the abandonment? (3) Give the iOS and Android distribution routes for the volunteer phase and the public phase. (4) If the reminder must still fire when the user has left the app's screen, which single-activity rule from Chapter 6 tells you the reminder cannot live in an activity's visible layer?

Step 1: maturity

One feature works, one crashes, one is missing: "only core functionality, or specific parts of the application are working. Major bugs are present." That is a prototype.

Step 2: the skipped question and the constraint

Elderly volunteers abandoning the app points at Value (how will they use it?) or at Analysis & Planning's target-audience question ("what are their implicit needs?"). Chapter 1's Constraint 3 explains the behaviour: mobile users drop off in distracted, non-work settings and "even if they intend to return later, users often forget and never come back, deleting the app after weeks without use".

Step 3: distribution

Volunteer phase: iOS Ad-Hoc Deployment (limited number of properly provisioned devices, for development and testing); Android signed APK installed directly (Android recognises signed APK files by default, Tutorial 1). Public phase: Apple App Store and Google Play; Android still requires signing with your own certificate.

Step 4: where the reminder lives

Chapter 6: only one activity can be in the foreground at any time, and an activity is a page in the foreground. A reminder that fires while the user is elsewhere therefore cannot be an activity's foreground job; the chapter's component list names the service as the no-user-interface, background component (music, download are its examples).

Full answer

(1) Prototype: partial functionality, major bug present. (2) Value / target audience (Analysis & Planning) was skipped; Constraint 3 (distractions, users who drop off forget to return) explains the abandonment. (3) Volunteers: iOS Ad-Hoc, Android signed APK sideload; public: Apple App Store and Google Play, Android signed with the developer's own certificate. (4) Because only one activity is in the foreground at a time and activities are foreground pages, a reminder firing elsewhere belongs to a background component: the service, per the Chapter 6 component list.

Trap

Part (4) tempts an invented answer ("use a broadcast receiver") or a vague one ("use the lifecycle"). Stay inside the course's vocabulary: the four application components are Activity, Service, Content provider, Broadcast receiver, and the one described as no user interface / background is the Service. Receivers are for system-wide events such as low battery.

Source: COMP3330_Ch01_Introduction.pdf, slides 42-43; COMP3330_Ch02_Lifecycle.pdf, slides 3-4, 12-15; COMP3330_Tutorial1.pdf, slide 8; COMP3330_Ch06_Activity_Fragment.pdf, slides 3, 5.
