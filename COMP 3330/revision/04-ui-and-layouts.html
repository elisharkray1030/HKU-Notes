UI and layouts

Every pixel an Android app shows belongs to a View, arranged by a layout into a tree. This page builds that mental model, then walks the XML that constructs it, the five layout types in the lecture, the dimension units that keep designs sane across screens, and the code that wires buttons to behaviour.

The mental model: a tree of rectangles

The visible parts of Android apps are Views: the basic building components for UI. Each activity/app is composed of one or more views; each view is an Android class in charge of a rectangle area, handling drawing, measurement, and user interactions (scroll, press, key, focus change). A ViewGroup is a view that contains other views. The lecture calls the leaf views widgets (button, field, selection) and the containers layouts (linear, relative). Drawing is done from the root.

Worked example from the lecture's own slide: a screen whose outer element is a ConstraintLayout containing a LinearLayout holding editText, editText2, button and textView. Classified: two ViewGroups (ConstraintLayout, LinearLayout) and four Views. Practise reading screens this way; it is the fastest route through any layout question.

Views have static appearance (layout, widget) and dynamic behaviour (event handling). The lecture's advice on learning them: look at examples, get a rough impression first and look up details later: breadth-first, non-linear.

Source: COMP3330_Ch04_Layout.pdf, slides 4-7.

XML layout anatomy

Layouts are specified in XML: a structured, human-readable document format like HTML. Why XML: static and visualisable (the Design view), more orthogonal code (one file handles display sizes, orientation, languages), easier to debug, and common in most situations. You can also modify layouts at run time: XML gives the default/initial layout, code can change it. The parallel to remember: an XML element or attribute corresponds to an Android class or method. A <TextView> element is a TextView widget; a <LinearLayout> element is a LinearLayout view-group.

XML
<?xml version="1.0" encoding="utf-8"?>
<LinearLayout xmlns:android="http://schemas.android.com/apk/res/android"
    android:layout_width="fill_parent"
    android:layout_height="fill_parent"
    android:orientation="vertical" >
  <TextView android:id="@+id/text"
      android:layout_width="wrap_content"
      android:layout_height="wrap_content"
      android:text="Hello, I am a TextView" />
  <Button android:id="@+id/button"
      android:layout_width="wrap_content"
      android:layout_height="wrap_content"
      android:text="Hello, I am a Button" />
</LinearLayout>

Two ways to close a tag, and the lecture flags both: the self-closing /> form and the explicit </EditText> form.

Ids, resources and inflation

android:id is needed if the view must be referenced by other views or by Java/Kotlin code. The notation android:id="@+id/my_button" unpacks as: @ = parse and expand, + = add to resources (R.java), so my_button becomes R.id.my_button in code. Likewise android:text="@string/my_button_text" pulls a string resource, and @drawable/hkulogo an image. At run time the XML is inflated for Activity.onCreate(): one line does it, no extra coding:

Java
public void onCreate(Bundle savedInstanceState) {
  super.onCreate(savedInstanceState);
  setContentView(R.layout.activity_main);
}

Size parameters: match_parent vs wrap_content

Every element sets layout_width and layout_height:

  • fill_parent / match_parent: the widget expands to take up as much space as is available within the layout element it has been placed in. The lecture notes match_parent is the name since API 8.
  • wrap_content: the view expands only far enough to contain the values (or child controls) it contains.
Pitfall

The slides use fill_parent in older examples and match_parent in newer ones for the same idea. They are the same behaviour under two names; only the name changed at API 8. Modern projects write match_parent: but if a question says fill_parent, answer in the question's words.

Source: COMP3330_Ch04_Layout.pdf, slides 8-17.

The five common layouts

The lecture teaches five: FrameLayout, LinearLayout, RelativeLayout, TableLayout and ConstraintLayout. ConstraintLayout is the default and recommended one (Android Studio 2.2+), but the others are taught because existing projects use them and some (LinearLayout) are easier to understand.

FrameLayout

Displays a single item at a time; elements are displayed overlapping. The lecture's example stacks an ImageView (the HKU logo) and a TextView on top of each other: exactly the "one item / overlapping" behaviour.

LinearLayout

Organizes elements along a single line, horizontal or vertical, set with android:orientation. The same widgets (Back button, First Name label + field, Last Name label + field) form a row when horizontal and a column when vertical.

RelativeLayout

Lays elements out by their relationships with one another and with the parent. Two families of attributes, and the exam expects you to tell them apart:

  • Relative to the parent: layout_alignParentBottom / Left / Right / Top, layout_centerHorizontal, layout_centerInParent, layout_centerVertical.
  • Relative to other elements: layout_above, layout_below, layout_toLeftOf, layout_toRightOf, layout_alignBaseline / alignBottom / alignLeft / alignRight / alignTop.

TableLayout

Organizes content into rows and columns. Rows are defined in the XML; columns are determined automatically: at least one column per element. So a row with two elements and a row with five elements give a table with two rows and five columns. android:layout_span makes an element occupy several columns (two elements with span 3 each give at least six columns); by default an element goes in the first unused column, and android:layout_column picks a specific one.

Exam angle

The lecture's own challenge: three TableRows (Back button; "First Name" label plus field; "Last Name" label plus field) give 3 rows and 3 columns. The column count is not just "the widest row has two elements": each label is pinned to column 1 with layout_column="1", the field after it lands in the first unused column, column 2, and the Back button occupies column 0. Columns 0, 1 and 2 all exist, so the table has three columns.

ConstraintLayout

The latest layout and the default in Android Studio: you drag components in and click "Infer Constraints" to define positions relative to the parent frame or other components. Relative positioning works by constraining each side: horizontal (left/start, right/end) and vertical (top, bottom, text baseline). Attribute naming pattern: layout_constraintX_toYOf: e.g. app:layout_constraintLeft_toRightOf="@+id/buttonA" pins buttonB's left to buttonA's right. Available constraints include left/start/right/end combinations, top/bottom combinations, and layout_constraintBaseline_toBaselineOf.

Three mechanics beyond pinning:

  • Margins: layout_marginStart / End / Left / Top / Right / Bottom; a margin can only be positive or zero and takes a dimension.
  • Bias: constraints to both sides are not a contradiction: they make the widget fill the gap, and app:layout_constraintHorizontal_bias="0.3" places it at 30% from the left.
  • Dimension ratio: set one dimension to 0dp (MATCH_CONSTRAINT) and give app:layout_constraintDimensionRatio, either a float (width:height) or "W:H". A button with layout_height="0dp" and ratio "1:1" gets height equal to width; "H,16:9" fixes the height at a 16:9 ratio to the width.
Pitfall

The ConstraintLayout XML on these slides is mixed: the first example uses the current androidx.constraintlayout.widget.ConstraintLayout, the later ones the old android.support.constraint.ConstraintLayout package, and the slides' doc link is old too. Current projects use androidx throughout. The behaviour and attribute names are unchanged; only the package moved.

ScrollView

A layout container for a view hierarchy that can be scrolled by the user, allowing content larger than the physical display. It is a FrameLayout, so you place one child in it containing the entire scrollable contents. That child may itself be a layout with a complex hierarchy. This is exactly how the Card 24 game's screen is built: outer ScrollView, inner LinearLayouts (Tutorial 2).

Source: COMP3330_Ch04_Layout.pdf, slides 18-35; COMP3330_Tutorial2.pdf, slides 11-14.

Dimension units: why dp and sp exist

Screens differ in physical size and pixel density, so raw pixels lie. The lecture's units:

  • px (pixels): actual pixels on the screen.
  • in / mm: physical size of the screen.
  • pt (points): 1/72 of an inch of physical size.
  • dp (density-independent pixels): abstract, based on physical screen density, relative to a 160 dpi screen: one dp is one pixel on a 160 dpi screen. The dp-to-pixel ratio changes with density (1 dp = 2 pixels on a 320 dpi screen) but not necessarily in direct proportion. The compiler accepts "dip" too; "dp" is preferred.
  • sp (scale-independent pixels): like dp, but also scaled by the user's font size preference. Recommended for font sizes, so text adjusts to both density and user preference.

Reusable values live in resource files: define <dimen name="textsize">15sp</dimen> in an XML file such as dimensions.xml, then set it in code with textView.setTextSize(getResources().getDimension(R.dimen.textsize));

Exam angle

Rule of thumb to write on your cheat sheet: layout sizes in dp, text sizes in sp, never px. "Why?" answers: dp absorbs screen density differences, sp additionally honours the user's font-size setting.

Source: COMP3330_Ch04_Layout.pdf, slides 37-41.

Wiring UI to code and event listeners

The XML builds the tree; code gives it behaviour. Three moves make up every example in this course:

  1. Find a view by id: findViewById(R.id.editText1): the bridge between @+id in XML and R.id in code.
  2. Create a listener object wrapping the behaviour: a View.OnClickListener with an onClick method.
  3. Attach it: button1.setOnClickListener(listener).

The lecture's random-number example, in both languages (note the Kotlin versions of the Java idioms: type parameters, as casts, ? nullable types, !! non-null assertions):

Kotlin
class MainActivity : AppCompatActivity() {
    private var random: Random? = null
    public override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        random = Random()

        val edit_text1 = findViewById<View>(R.id.editText1) as EditText
        val button1 = findViewById<View>(R.id.button1) as Button

        val listener = View.OnClickListener {
            edit_text1.setText(random!!.nextInt(100).toString())
        }
        button1.setOnClickListener(listener)
    }
}
Java
public class MainActivity extends AppCompatActivity {
    private Random random;

    public void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_main);
        random = new Random();

        final EditText edit_text1 = (EditText) findViewById(R.id.editText1);
        final Button button1 = (Button) findViewById(R.id.button1);

        Button.OnClickListener listener = new Button.OnClickListener() {
            public void onClick(View dummy) {
                edit_text1.setText(String.valueOf(random.nextInt(100)));
            }
        };
        button1.setOnClickListener(listener);
    }
}

A second wiring style exists: put android:onClick="calc" on the button in XML and name a calc(View v) method in the activity, as Tutorial 1's BMI calculator does. Two routes to the same destination: a listener object in code, or an attribute reference to a method.

For collections of widgets (Card 24's four card buttons), the tutorial pattern is an array of ImageButtons: private lateinit var cards: Array<ImageButton>. The lateinit modifier promises the variable is initialized later (in onCreate(), via one findViewById per element). Listeners then share one handler: cards[0].setOnClickListener { clickCard(0) }.

Discuss

Take a position: for a simple form screen, LinearLayout is the better teaching and production choice than ConstraintLayout, and the lecture's own reason (it is easier to understand) also justifies using it in real projects. Evidence that would change your mind: the form must survive rotation, translation to longer languages, or tablet widths: cases where relationships between views matter more than order.

Check yourself

Q1

A view has android:layout_width="wrap_content" and text "Go". How wide is it?

wrap_content expands "only far enough to contain the values (or child controls) it contains". match_parent/fill_parent is the one that takes all available space.

Q2

Which attribute set belongs to "position relative to another element" in RelativeLayout?

above/below/toLeftOf/toRightOf/align* reference another element. alignParent* and center* reference the parent container; margins are offsets, not relationships.

Q3

In android:id="@+id/my_button", what does the + mean?

"@: parse and expand, +: add to resource (i.e., R.java)". This is what makes findViewById(R.id.my_button) possible.
