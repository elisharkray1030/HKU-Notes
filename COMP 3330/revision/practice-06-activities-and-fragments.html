Practice: activities and fragments

Chapter 6 is the mechanics of moving around an app: which callbacks fire and when, how intents route between screens, how data rides along, and how fragments let you swap pieces of a screen. The exam tests all four as one story.

Background: Activities and fragments.

Quiz: callbacks, intents, fragments

Q1

Which statement matches the chapter's simple understanding of an activity?

Chapter 6, slide 5: "A simple understanding of an activity is a page in the foreground" and "Only one activity can be in the foreground at any time." The other options are the Service, Content provider and Broadcast receiver from the component list.

Q2

Which is an explicit intent?

Chapter 6: explicit intents are used within the application to switch from one activity to another and take a context plus the target activity (Java: new Intent(this, FooActivity.class)). Implicit intents specify only the action; the system picks the component. Extras do not make an intent explicit.

Q3

Which fragment callbacks must you implement at minimum, per the chapter?

The chapter lists "You should implement at least the following": onCreate() to initialize essential components the fragment should retain across pause/stop/resume; onCreateView(), called when it is time for the fragment to draw its UI for the first time. onPause() is listed as optional ("first indication that the user is leaving the fragment").

Q4

In what order do the callbacks fire on a cold start of one activity?

Chapter 6's lifecycle list is ordered and labelled: onCreate() = enter memory, onStart() = become visible, onResume() = get focus / foreground; then onPause() = lose focus, onStop() = become invisible, onDestroy() = leave memory.

Q5

The sender writes myIntent.putExtra("ID", 6999). How should the receiver read it?

The receiver side reads val bundle: Bundle? = intent.extras and pulls values with typed getters; the chapter's own note says "Can use getInt("ID") if ID is an integer / Can use getLong("ID") if ID is a long integer". 6999 is an integer extra, so getInt is the getter that matches. intent.data is for the URI, not extras.

Source: COMP3330_Ch06_Activity_Fragment.pdf, slides 3, 5, 7, 11, 38, 43.

Exercise 1: the full callback trace

Exercise 1 skill: predicting callback order across a screen change medium

Activity A is a note list and Activity B is the editor, opened full screen. Trace, in order, every callback from the moment the user taps the app icon with A as the entry activity, to the moment B is showing and interactive. Then say: (a) where A should flush its draft to the database and why; (b) which of A's callbacks do not fire if the phone shows A and B side by side so A stays visible.

Step 1: cold start of A

onCreate() (A enters memory) → onStart() (A becomes visible) → onResume() (A gets focus; it is in the foreground).

Step 2: the tap starts B

Chapter 6's coordination example: A's onPause() executes first (A loses focus), then B's onCreate(), onStart(), onResume() execute in sequence, and B now has user focus.

Step 3: A's fate

If A is no longer visible on screen, its onStop() executes (A becomes invisible). It is not destroyed: onDestroy() means leave memory and is not part of this flow.

Step 4: answers (a) and (b)

(a) The flush goes in onPause(): it is A's only callback guaranteed to run before B is created, and the lecture says it plainly: "if A needs to write to a DB before B starts, use onPause() instead of onStop()". (b) Side by side, A is visible but without focus, so A's onStop() does not fire; onCreate/onStart stay as they were.

Full answer

A.onCreate() → A.onStart() → A.onResume() → [tap] → A.onPause() → B.onCreate() → B.onStart() → B.onResume() → A.onStop() (only if A is no longer visible). (a) Write the draft in onPause(). (b) In the side-by-side case A.onStop() does not fire; A stays visible without focus.

Trap

The plausible wrong order is A.onPause() → A.onStop() → B.onCreate() ... The chapter puts B's entire creation between A's pause and A's stop. The order matters in practice: anything you defer to onStop() happens too late to influence B's startup.

Tip

Remember the labels, not just the names: enter memory, become visible, get focus, lose focus, become invisible, leave memory. Every ordering question is answered from those six labels.

Source: COMP3330_Ch06_Activity_Fragment.pdf, slides 6-8.

Exercise 2: passing a result to the next screen

Exercise 2 skill: explicit intents and typed extras, both languages medium

A quiz app has QuizActivity and ResultActivity (already declared in AndroidManifest.xml). When the user finishes, QuizActivity must open ResultActivity showing the final score (an Int) and the player's name (a String). Write the sender's click handler and the receiver's onCreate reading both extras, following the chapter's explicit-intent steps and its extras code. Then: what does ResultActivity read if QuizActivity instead just sent a URL as intent data?

Step 1: follow the explicit-intent steps

Create the layout for the new activity; define the new activity in the manifest; in the calling activity create an Intent instance and start it; the called activity creates another Intent instance to return. The Intent needs a context and the name of the activity to start. (The lecture's word "return" is loose: as the re-teach page notes, that second Intent starts a new instance of the calling activity; the real way back is the system Back button.)

Step 2: attach extras with explicit types

putExtra("Score", score) with score: Int and putExtra("Name", name) with name: String. The receiver obtains the Bundle via intent.extras and uses matching getters.

Step 3: read the data

The chapter's receiver shape: val bundle: Bundle? = intent.extras; bundle?.let { bundle.apply { ... } }. The safe call handles a missing extras bundle (Chapter 5's null safety in action).

Full answer
Kotlin: sender (QuizActivity)
finish.setOnClickListener {
    val myIntent = Intent(this, ResultActivity::class.java)
    myIntent.putExtra("Score", score)      // Int
    myIntent.putExtra("Name", playerName)  // String
    startActivity(myIntent)
}
Kotlin: receiver (ResultActivity)
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setContentView(R.layout.activity_result)
    val output = findViewById<TextView>(R.id.resultText)
    val bundle: Bundle? = intent.extras
    bundle?.let {
        bundle.apply {
            val score: Int = getInt("Score")
            val name: String? = getString("Name")
            output.text = "Score: $score ($name)"
        }
    }
}
Java: sender (QuizActivity)
finish.setOnClickListener(new View.OnClickListener() {
    public void onClick(View v) {
        Intent myIntent = new Intent(QuizActivity.this, ResultActivity.class);
        myIntent.putExtra("Score", score);      // int
        myIntent.putExtra("Name", playerName);  // String
        startActivity(myIntent);
    }
});
Java: receiver (ResultActivity)
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_result);
    TextView output = (TextView) findViewById(R.id.resultText);
    Bundle bundle = getIntent().getExtras();
    if (bundle != null) {
        int score = bundle.getInt("Score");
        String name = bundle.getString("Name");
        output.setText("Score: " + score + " (" + name + ")");
    }
}

If QuizActivity sent only a URL as intent data (Intent(this, ResultActivity::class.java).apply { data = Uri.parse(url) } or the chapter's two-argument Intent(action, uri) style), the receiver reads it with val url: Uri? = intent.data (Kotlin) or getIntent().getData() (Java), not from the extras bundle.

Trap

Copying the lecture's receiver snippet verbatim for an integer extra. Its sender puts an Int (myIntent.putExtra("ID", 6999)) but the snippet reads it with getString("ID"), and the very next line of the slide says "Can use getInt("ID") if ID is an integer". The durable rule: the getter must match the type given to putExtra: getInt for 6999. Note also that intent.data and intent.extras are different channels: data carries the Uri, extras carry your key-value pairs.

Source: COMP3330_Ch06_Activity_Fragment.pdf, slides 28-34 (explicit intent code), 37-40 (extras, typed getters, arrays and objects), 19 (intent.data).

Exercise 3: implicit intents and matching filters

Exercise 3 skill: deciding which component an implicit intent reaches hard

An app declares three activities in AndroidManifest.xml:

XML
<activity android:name=".MainActivity" android:exported="true">
  <intent-filter>
    <action android:name="android.intent.action.MAIN" />
    <category android:name="android.intent.category.LAUNCHER" />
  </intent-filter>
</activity>
<activity android:name=".ViewerActivity" android:exported="true">
  <intent-filter>
    <action android:name="android.intent.action.VIEW" />
    <action android:name="hkucs.studyroom.OPEN" />
    <category android:name="android.intent.category.DEFAULT" />
    <data android:scheme="http" />
  </intent-filter>
</activity>
<activity android:name=".PlainActivity" />

Three sends follow: (i) Intent(Intent.ACTION_VIEW, Uri.parse("http://www.hku.hk")); (ii) Intent("hkucs.studyroom.OPEN", Uri.parse("http://www.hku.hk")); (iii) Intent(this, PlainActivity::class.java). For each, name every activity that can receive it and why. Then say how ViewerActivity reads the URL.

Step 1: explicit versus implicit

(iii) is explicit (it names the component), so it goes to PlainActivity regardless of filters. (i) and (ii) are implicit: they name only an action (plus data), so the system compares each intent against components' intent filters and picks the best match.

Step 2: match (i) against the filters

Its action is android.intent.action.VIEW and its data scheme is http. ViewerActivity's filter advertises VIEW and declares scheme http, so it matches. MainActivity's filter advertises MAIN/LAUNCHER only, so no match. PlainActivity has no filters, and "if a component does not have any intent filters, it can receive only explicit intents", so it is excluded.

Step 3: match (ii) against the filters

The first argument of Intent("hkucs.studyroom.OPEN", uri) is the action string. The system looks for intent filters containing that action; ViewerActivity's filter lists it, so ViewerActivity is invoked, the same pattern as the lecture's hkucs.myintentfilter example. The Uri rides as intent data.

Step 4: reading the URL

In ViewerActivity: val url: Uri? = intent.data (Kotlin) or getIntent().getData() (Java); the lecture then shows label.text = url.toString().

Full answer

(i) ViewerActivity only (action VIEW + http scheme both match its filter). (ii) ViewerActivity only (its filter advertises the custom action). (iii) PlainActivity (explicit, filters irrelevant). MainActivity receives none of these; it is the launcher because it holds action MAIN with category LAUNCHER. ViewerActivity reads the URL via intent.data (Kotlin) / getIntent().getData() (Java) into a Uri, then uses it anywhere.

Trap

Two traps. First, treating "hkucs.studyroom.OPEN" as the name of a filter: it is the action inside an intent object, matched against the actions listed in filters; filters have no names of their own. Second, assuming PlainActivity can still catch implicit intents because it is in the same app: no filters means explicit intents only.

Exam

One nuance visible in the lecture's manifests: implicit intents started with startActivity carry category DEFAULT, and every filter meant to receive them includes <category android:name="android.intent.category.DEFAULT" />. Copy that pattern in your answers; the LAUNCHER category belongs only to the MAIN filter.

Source: COMP3330_Ch06_Activity_Fragment.pdf, slides 11-12 (explicit vs implicit), 17-27 (intent filters, manifests, code).

Exercise 4: fragments and the back stack

Exercise 4 skill: reasoning about FragmentTransaction and addToBackStack hard

The chapter's Fragment example has an activity layout with a FrameLayout region (@+id/frame_container) and two tap targets. Tapping "Fragment 1" runs addFragment(FragmentOne(), false, "one"); tapping "Fragment 2" runs addFragment(FragmentTwo(), false, "two"), where the method is:

Kotlin
fun addFragment(fragment: Fragment?, addToBackStack: Boolean, tag: String?) {
    val manager: FragmentManager = supportFragmentManager
    val ft: FragmentTransaction = manager.beginTransaction()
    if (addToBackStack) {
        ft.addToBackStack(tag)
    }
    if (fragment != null) {
        ft.replace(R.id.frame_container, fragment, tag)
    }
    ft.commitAllowingStateLoss()
}

(a) With the code as written, what is on screen after tapping "Fragment 1" then "Fragment 2", and what happens when the user presses the Back button? (b) What changes if both calls pass true? (c) In which order must the three FragmentTransaction calls happen, and what do each of the fragment's two mandatory callbacks do?

Step 1: trace the two taps

Each tap begins a transaction and calls replace on the region: FragmentOne is placed in frame_container, then FragmentTwo replaces it. The tag ("one"/"two") identifies the fragment in the transaction. Final screen: FragmentTwo only; replace swaps the region's content.

Step 2: the Back button

addToBackStack is the call that saves a transaction so Back can reverse it, and both calls pass false, so neither transaction is on the back stack. Pressing Back therefore does not restore FragmentOne; it behaves like the activity's own back (leaving the screen).

Step 3: with true

Each transaction is saved. Back then undoes the most recent one: FragmentTwo is removed and FragmentOne is shown again; Back again undoes the first transaction, emptying the region.

Step 4: the call order and the callbacks

The chapter's steps: obtain the FragmentManager (supportFragmentManager), beginTransaction(), then replace with the region id, fragment and tag, optionally addToBackStack(tag), then commit. The course code uses commitAllowingStateLoss(). Mandatory callbacks: onCreate() initializes essential components the fragment should retain across pause/stop/resume; onCreateView() is called when it is time to draw the fragment's UI for the first time and returns the inflated layout (inflater.inflate(R.layout.fragment_fragment_one, container, false) in the example).

Full answer

(a) FragmentTwo is on screen (it replaced FragmentOne). Back does not bring FragmentOne back, because neither transaction called addToBackStack. With the false arguments in the lecture's own MainActivity, Back leaves the activity's screen. (b) With true, Back undoes the latest replace (FragmentTwo → FragmentOne), and another Back undoes the first (region empty). (c) beginTransaction → [addToBackStack(tag) if wanted] → replace(region id, fragment, tag) → commitAllowingStateLoss(). The fragment must implement onCreate() (init retained components) and onCreateView() (inflate and return its UI).

Trap

The sample code is the trap. Read addFragment(FragmentOne(), false, "one") carefully: the second argument is the addToBackStack flag and it is false in the lecture's wiring, so the "obvious" answer (Back returns to the previous fragment) is wrong for this code. Back-stack membership is opt-in per transaction, not a property of fragments.

Source: COMP3330_Ch06_Activity_Fragment.pdf, slides 42-51 (fragment concept, lifecycle, basic steps, example code).

Mixed exercise: one flow through the whole chapter

Exercise 5 skill: combining callbacks, intents, extras and null handling hard

This one pulls Chapter 4's findViewById wiring and Chapter 5's null safety in with Chapter 6. A flashcard app has StudyActivity (the question screen) and StatsActivity. The user taps "Stats"; the app must open StatsActivity, show "Cards reviewed: N" where N is an Int kept in StudyActivity, and the UI must be wired through @+id views as usual. (1) List the callback sequence of StudyActivity and StatsActivity from the tap to the stats text being visible. (2) Write the send and read code for N in the chapter's shape, with the safe handling of a missing bundle. (3) If StatsActivity's layout has a TextView @+id/statsText, what does the wiring look like and where? (4) The designer wants the two screens side by side on tablets using fragments instead. Name the two mandatory fragment callbacks and the one call that makes Back return to the previous fragment.

Step 1: callbacks

StudyActivity.onPause() → StatsActivity.onCreate() → onStart() → onResume() (stats text set inside onCreate) → StudyActivity.onStop() if no longer visible.

Step 2: extras with types

Send: Intent(this, StatsActivity::class.java) plus putExtra("Reviewed", reviewed) with reviewed: Read: val bundle: Bundle? = intent.extras; bundle?.let { ... getInt("Reviewed") ... }. Matching getter, safe call for the possibly missing bundle.

Step 3: wiring

In StatsActivity.onCreate, after setContentView(R.layout.activity_stats): val statsText = findViewById<TextView>(R.id.statsText); the id comes from @+id/statsText in the XML (Chapter 4: "@" parse and expand, "+" add to R).

Step 4: the fragment route

Mandatory: onCreate() and onCreateView(). Back behaviour: ft.addToBackStack(tag) on each transaction before commit.

Full answer

(1) StudyActivity.onPause() → StatsActivity.onCreate() → StatsActivity.onStart() → StatsActivity.onResume() → StudyActivity.onStop() if it ended up invisible. (2) Sender: val myIntent = Intent(this, StatsActivity::class.java); myIntent.putExtra("Reviewed", reviewed); startActivity(myIntent). Receiver: val bundle: Bundle? = intent.extras; bundle?.let { val n: Int = getInt("Reviewed"); statsText.text = "Cards reviewed: $n" }. (3) After setContentView, findViewById<TextView>(R.id.statsText) in onCreate. (4) onCreate() and onCreateView() are mandatory; addToBackStack(tag) before committing the transaction gives the reverse-on-Back behaviour.

Trap

Setting the text before setContentView, or reading extras before super.onCreate and setContentView have run. The lecture's receiver code reads the bundle and touches the widget inside onCreate after setContentView; and a missing extras bundle is a real possibility, and the bundle?.let form is the chapter's own answer, which is Chapter 5 null safety doing real work.

Source: COMP3330_Ch06_Activity_Fragment.pdf, slides 8, 33-38, 43-44; COMP3330_Ch04_Layout.pdf, slides 9-10, 17; COMP3330_Ch05_Syntax.pdf, slides 13-17.
