Practice: Card 24 and Flutter

The Card 24 case study is where the whole course comes together: rules turned into input validation, validation into state, state into listeners. Then Tutorial 4 opens a second toolkit, Flutter, and asks you to think again about widgets and state. Both halves are drilled here.

Background: Card 24 and Flutter. The Card 24 UI work is drilled in UI and layouts.

Quiz: rules, code and Flutter

Q1

When does the player win a game of Card 24, per the application specification?

Tutorial 2 lists three conditions together: no error in the formula, all four cards selected exactly once, and the result equals 24. Any one alone is not a win; the code even checks the value with a tolerance (Tutorial 3) instead of a bare equality.

Q2

What is the evaluation order the game's specification requires?

Tutorial 2: "the formula should be evaluated in the order of 'bracket items' before 'multiplication/division' before 'addition/subtraction'", with the worked example (1) + (11 - 2) x 6 = 55 evaluated as (1) = 1, (11 - 2) = 9, 9 x 6 = 54, 1 + 54 = 55.

Q3

checkInput computes a double result ca. Which condition does the tutorial use to declare "Correct Answer"?

Tutorial 3's checkInput: parse and evaluate with JEP, cast the result to Double, then "return abs(ca - 24) < 1e-6". The tolerance exists because the evaluator produces floating-point doubles, where a correct construction can land a hair away from 24.

Q4

In Tutorial 4's Flutter example, what is setState() for?

Tutorial 4: "setState() is the method in Flutter used to notify the framework that the state has changed and the UI needs to be rebuilt", and the flow is: button callback → state modified → setState() → build() re-executed → new _display rendered.

Q5

Which statement about Flutter and Dart matches the course?

Tutorial 4: Dart can be compiled into native machine code; Flutter does not rely on a browser or a JavaScript runtime; the Dart SDK is bundled with Flutter; and hot reload lets you update code and see changes almost instantly without losing state. Flutter itself is a UI toolkit from Google with a C++ engine rendering via Skia (Chapter 3).

Exercise 1: validating button streams

Exercise 1 skill: applying the input-limitation rules to press sequences medium

The specification's two input rules are: a card or an open bracket "(" may be selected only when it is the first item in the formula or it follows an arithmetic symbol or "("; and a symbol (+, -, x, /) or a close bracket ")" may be selected only when the last previously selected item is a card or ")". The four cards are 13, 5, 2, 1. Classify each press stream as valid or invalid, naming the first violating press and the rule it violates. For valid streams, write the formula and evaluate it.

(a) 13, -, 5, x, (, 2, +, 1, )
(b) 5, +, +, 1
(c) (, ), 2
(d) 5, 2 (two card presses in a row)
(e) (, 13, -, 5, ), x, 2

Step 1: state the two rules as tests

Before pressing item X: if X is a card or "(", the previous item must be nothing (X is first), a symbol, or "(". If X is a symbol or ")", the previous item must be a card or ")".

Step 2: walk each stream press by press

(a) 13 first; "-" after card 13; 5 after symbol; "x" after card 5; "(" after symbol; 2 after "("; "+" after card 2; 1 after symbol; ")" after card 1. All pass. (b) The second "+" follows "+", a symbol, violating the operator rule (needs card or ")"). (c) ")" follows "(", violating the operator rule. (d) The second card press (2) follows a card, violating the card rule (needs symbol or "("). (e) ")" follows 5, which is a card, so it is allowed; then "x" follows ")", also allowed. All pass.

Step 3: evaluate the valid streams

(a) "13-5x(2+1)": brackets first, (2+1) = 3; multiplication/division next, 5x3 = 15; addition/subtraction last, 13-15 = -2. (e) "(13-5)x2": (13-5) = 8, then 8x2 = 16.

Full answer

(a) Valid; "13-5x(2+1)" = -2. (b) Invalid at the second "+": an operator may follow only a card or ")". (c) Invalid at ")": same operator rule, since the previous item is "(". (d) Invalid at the 2: a card may follow only a symbol or "(" (or be first). (e) Valid; "(13-5)x2" = 16. Neither valid formula reaches 24, so pressing "=" would show "Wrong Answer". But a wrong answer and an invalid formula are different failures in the spec.

Trap

Stream (e) looks suspicious because ")" appears before "x", but the rules allow a symbol after ")". The naive over-strict reading ("a formula must end with a card") forbids it; the stated rules do not. Conversely, stream (d) looks harmless because both presses are legal buttons, but the card rule forbids card-after-card. Judge against the two clauses, not against how the string looks.

Why it matters

The specification motivates these rules as preventing "non-sense player input" like "()1+/12". Each rule clause is a guard you will implement in the listeners: this is the design step before the code.

Exercise 2: evaluating the way the game does

Exercise 2 skill: order of operations and the floating-point win test hard

Cards dealt: 8, 3, 8, 3. The player builds the formula "8/(3-8/3)" and presses "=". The evaluator computes in double-precision arithmetic and checkInput accepts when abs(ca - 24) < 1e-6. (a) Show the evaluation steps in the spec's order. (b) In double arithmetic the computed value is not exactly 24; it differs from 24 by about 1.1 x 10^-14. Does the player win? (c) Would the player win if the code tested ca == 24 instead? (d) Classify these three computed results as win or lose: 23.9999995, 24.0000009, 23.99999.

Step 1: the spec's evaluation order

Brackets first: 8/3 inside the bracket evaluates first under multiplication/division-before-subtraction, so (3 - 8/3) = (3 - 2.666...) = 0.333...; then the division outside: 8 / 0.333... = 24. The mathematics is exact: 8 / (1/3) = 24.

Step 2: what the doubles actually hold

8/3 cannot be represented exactly in binary floating point, so the intermediate 3 - 8/3 is slightly above 1/3, and the final quotient lands slightly below 24, about 23.99999999999999, roughly 1.1 x 10^-14 short.

Step 3: apply the code's test

abs(ca - 24) is about 1.1 x 10^-14, which is less than 1e-6, so checkInput returns true: "Correct Answer", and the game deals a new hand. An equality test ca == 24 would return false for this perfectly good formula.

Step 4: the three boundary cases

23.9999995: |diff| = 5 x 10^-7 < 10^-6 → win. 24.0000009: |diff| = 9 x 10^-7 < 10^-6 → win. 23.99999: |diff| = 10^-5, not less than 10^-6 → lose.

Full answer

(a) Inner division 8/3 first (multiplication/division before subtraction), then 3 - that, then 8 divided by it = 24 mathematically. (b) Yes: the player wins: the computed value is within 1e-6 of 24. (c) No: ca == 24 would reject it, which is why the tutorial uses a tolerance. (d) 23.9999995 wins; 24.0000009 wins; 23.99999 loses.

Trap

Two traps. First, mental arithmetic "it equals 24 exactly, so the double must be 24": the win test exists precisely because the double is not 24. Second, flipping the comparison to ca <= 24 + 1e-6 or rounding first: the spec's acceptance rule is the strict inequality abs(ca - 24) < 1e-6, and 23.99999 shows that a visibly wrong answer can still be a loss even though it is "close".

Source: COMP3330_Tutorial2.pdf, slide 5 (evaluation order); COMP3330_Tutorial3.pdf, slides 12-14 (checkInput with JEP and tolerance).

Exercise 3: reading the Card 24 code

Exercise 3 skill: tracing real activity code state by state medium

Tutorial 3's code, trimmed to the parts you need:

Kotlin
private lateinit var data: Array<Int>   // card values 1..13
private lateinit var card: Array<Int>   // card identifiers 1..52
private lateinit var imageCount: Array<Int>

private fun setClear() {
    var resID: Int
    expression.text = ""
    for (i in 0..3) {
        imageCount[i] = 0
        resID = resources.getIdentifier("card" + card[i], "drawable", packageName)
        cards[i].setImageResource(resID)
        cards[i].isClickable = true
    }
}

private fun clickCard(i: Int) {
    if (imageCount[i] == 0) {
        val resId = resources.getIdentifier("back_0", "drawable", packageName)
        cards[i].setImageResource(resId)
        cards[i].isClickable = false
        val value = data[i]
        expression.append(value.toString())
        imageCount[i]++
    }
}

After pickCard() has dealt data = [4, 5, 9, 10] and card = [4, 5, 9, 10] and called setClear(): (a) what is the state of the four buttons and the expression TextView? (b) The user taps card button 1 twice, then card button 3. What is on screen and what is imageCount? (c) The user presses "Clear". State everything setClear() changes. (d) When "=" is pressed, how does the code know that all four cards were used exactly once?

Step 1: initial state

setClear() empties the expression text, zeroes imageCount, and gives each button its face image "card" + card[i] (card4, card5, card9, card10) with isClickable = true. imageCount = [0, 0, 0, 0].

Step 2: the taps

Tap 1 on button 1: image becomes back_0, isClickable false, expression appends data[1] = "5", imageCount[1] = 1. The second tap on button 1 does nothing: the card is not clickable, and even if it were, clickCard's imageCount[i] == 0 guard fails. Tap on button 3: expression becomes "59" (appends data[3] = 9), imageCount = [0, 1, 0, 1].

Step 3: Clear

expression.text = ""; every imageCount[i] = 0; every button's image reset to its "card" + card[i] face; every button clickable again. The deal itself (data and card arrays) is unchanged; Clear resets the round, not the cards.

Step 4: the all-four-cards check

Each successful clickCard(i) increments imageCount[i] exactly once and disables the button, and the guard makes a second increment impossible. So "used exactly once" is equivalent to imageCount == [1, 1, 1, 1] (or its sum being 4) at "=" time. Tutorial 3 leaves this as Task 5.2 for the student to add.

Full answer

(a) All four buttons show their face images and are clickable; the expression TextView is empty; imageCount = [0, 0, 0, 0]. (b) Button 1 shows back_0 and is disabled; button 3 shows back_0 and is disabled; the expression reads "59"; imageCount = [0, 1, 0, 1]. (c) setClear() clears the expression text, zeroes all of imageCount, restores each button's face image, and makes each clickable again. (d) Because clickCard increments imageCount[i] once and disables the button, the check at "=" is imageCount == [1, 1, 1, 1] (or sum == 4).

Trap

Confusing the two arrays: data holds the 1-13 values that go into the expression; card holds the 1-52 identifiers used to build the drawable name "card" + card[i]. A second trap is checking the formula string instead of imageCount: the string does not record which card buttons were pressed (two cards can share the same value, as in the dealt 4 and 4 of a real deal).

Pitfall in the tutorial

Tutorial 2's initCardImage calls resources.getIdentifier("back_0", "drawable", "hk.hkucs.card24") with a hardcoded package name (its own note says to replace it with your package name), while Tutorial 3's methods pass packageName. If your application's package differs, the hardcoded form silently finds no resource, so prefer packageName.

Exercise 4: the Flutter state loop

Exercise 4 skill: reasoning about widgets, state and rebuilds in Flutter easy

Tutorial 4's example app shows the number a user entered, held in a field _display. (a) Put the loop in order: build() re-executed; user clicks the button; button callback triggered; state modified; setState() called; new _display rendered. (b) A student updates _display in the callback but never calls setState(). What does the user see, and why? (c) Name what MaterialApp gives the app and what hot reload gives the developer.

Step 1: order the loop

User clicks the button → button callback triggered → state modified → setState() called → build() re-executed → new _display rendered. This is Tutorial 4's own sequence.

Step 2: the missing setState

setState() is what notifies the framework that the state has changed and the UI needs to be rebuilt. Without it the framework is never told, build() is not re-executed, and the old value stays on screen even though the field changed.

Step 3: MaterialApp and hot reload

MaterialApp is one of the widgets in Flutter's Material component library, providing a Material Design interface and default theme. Hot reload: update code and see changes almost instantly, without losing state.

Full answer

(a) Click → callback → state modified → setState() → build() re-executed → new _display rendered. (b) The screen keeps showing the old value: the field changed but the framework was not notified, so no rebuild happened. (c) MaterialApp supplies the Material Design interface and default theme; hot reload lets the developer see code changes almost instantly without losing state.

Trap

"Flutter is a JavaScript framework" and "hot reload restarts the app" are both wrong per Tutorial 4: apps are written in Dart (compiled to native machine code, no browser or JS runtime) and hot reload preserves state. If a change requires losing state, that is a restart, not a reload.

Mixed exercise: hardening Card 24 before submission

Exercise 5 skill: combining rules, code, lifecycle and layout into one fix list hard

Current state of the Card 24 app: the deal is hardcoded to cards 4, 5, 9, 10; the game does not enforce using all four cards; the layout has a ScrollView wrapping linear rows (Tutorial 2); and the team wants a "High scores" screen showing the winning streak, passed as an Int extra. (1) What must pickCard() do to satisfy the specification's "randomly pick 4 non-duplicate cards from totally 52 poker cards (excluding two jokers)"? (2) Where does the all-four-cards check go, and what exactly does it test (Exercise 3's answer)? (4) Write the intent and extras code to open the high-score screen, and say where its TextView is found. (5) Which single-child rule must the layout keep?

Step 1: the random deal

Values run 1-13 with A/J/Q/K = 1/11/12/13 and the deck has 52 distinct cards. pickCard() must draw four distinct card identifiers from 52 (non-duplicate, as the specification says), set data[i] to each card's value and card[i] to its identifier, then call setClear(). The tutorial's fixed array is a test stub, which is exactly what Task 5.1 asks you to replace.

Step 2: the all-cards check

It goes where "=" is handled, before or alongside checkInput: the specification's win conditions are checked together. The test: imageCount == [1, 1, 1, 1], since each successful clickCard increments one entry exactly once. Failing it means the player loses even if the formula equals 24.

Step 3: maturity

All functionality is present except two known pieces and testing has been light: that matches Beta ("most functionality is now complete and has had at least light testing and bug fixing; major known issues may still be present") rather than Release Candidate ("all functionality is complete and tested").

Step 4: the high-score screen

Explicit intent inside the app (Chapter 6: explicit intents are the usual way to do page switching in one project): Intent(this, HighScoreActivity::class.java) with putExtra("Streak", streak) (Int), and the receiver reads intent.extras and getInt("Streak"). The TextView is found in HighScoreActivity.onCreate after setContentView, via findViewById(R.id....), because its XML declares an @+id for views referenced from code.

Step 5: the layout rule

Keep exactly one child inside the ScrollView (it is a FrameLayout): the outer LinearLayout that contains all the rows.

Full answer

(1) Replace the stub with a random draw of 4 non-duplicate identifiers from 52, deriving each value 1-13 (A/J/Q/K = 1/11/12/13) and calling setClear(). (2) In the "=" handler: require imageCount == [1, 1, 1, 1] before accepting checkInput's result. (3) Beta: most functionality complete, light testing done, known issues (the two tasks) outstanding. (4) The intent and extras, Kotlin and Java:

Kotlin
// sender (MainActivity)
val myIntent = Intent(this, HighScoreActivity::class.java)
myIntent.putExtra("Streak", streak)   // Int
startActivity(myIntent)

// receiver (HighScoreActivity.onCreate)
val bundle: Bundle? = intent.extras
bundle?.let {
    bundle.apply {
        val streak: Int = getInt("Streak")
        val label = findViewById<TextView>(R.id.highScoreText)
        label.text = "Streak: $streak"
    }
}
Java
// sender (MainActivity)
Intent myIntent = new Intent(MainActivity.this, HighScoreActivity.class);
myIntent.putExtra("Streak", streak);   // int
startActivity(myIntent);

// receiver (HighScoreActivity.onCreate)
Bundle bundle = getIntent().getExtras();
if (bundle != null) {
    int streak = bundle.getInt("Streak");
    TextView label = (TextView) findViewById(R.id.highScoreText);
    label.setText("Streak: " + streak);
}

The receiver's TextView is found after setContentView via findViewById, because the XML declares an @+id for views referenced from code. (5) One child inside the ScrollView.

Trap

Checking "all four cards used" by counting characters in the expression string or by scanning for four distinct values. Two different cards can share a value (a real 52-card deal can produce 4, 4, 4, 4), and brackets and operators change the string length. The state that records card usage is imageCount, and the disable-on-tap behaviour is what makes it exact.
