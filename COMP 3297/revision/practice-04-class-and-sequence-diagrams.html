Class and sequence diagrams: practice

Notation is graded in this course, so these exercises drill it: multiplicities read in both directions, message styles that say what they mean, and class boxes with visibility and types. The diagrams in the answers use the lecture's notation.

Background: Class and sequence diagrams.

Quiz

Q1

A class diagram shows an association "books" between Attendee and Ticket, with "1" at the Attendee end and "0..*" at the Ticket end. The "0..*" at the Ticket end means:

The trap is the reading direction. A multiplicity at one end counts instances at that end, for one instance at the other end. So "0..*" next to Ticket says how many Tickets per Attendee; "1" next to Attendee says each Ticket is booked by exactly one Attendee, which is the last option's fact, but not what "0..*" itself means.

Q2

In a sequence diagram, a message drawn as a solid line with an open arrowhead, after which the sender carries on without waiting, is:

The lecture's three styles: synchronous call is a solid line with a filled arrowhead (the sender must wait for a response to continue); asynchronous call is a solid line with an open arrowhead (the sender does not wait for a return value); reply message is a dashed line with an open arrowhead. Which style fits a given use case is a modelling choice, but the drawing must match the meaning.

Q3

A class diagram shows Patient record with a hollow diamond on its line to Consultation. This relationship is:

The lecture draws aggregation as a hollow diamond at the whole end and reads it as "one object (the whole) is composed of other objects (the parts)". Generalization is the "is-a" relationship and is drawn as a line with a hollow triangle pointing up to the more general class. In standard UML a filled diamond means the stricter composition; the lecture's diagram uses the hollow form, so name what you see.

Q4

A class box contains the line "- viewInfo(PID:int):String". What is it?

Visibility: "+" is public, "-" is private. A line in the operations compartment with parentheses is an operation; "PID:int" inside the parentheses is a parameter with its type; the type after the colon at the end is the return type. The trap is reading "int" as the return type and missing the real one, String, at the far right.

Guided exercises

Exercise 1 skill: building a class diagram medium

ConfTicket sells conference tickets. An Attendee books Tickets for Events. Each Ticket is for exactly one Event; an Event offers many Tickets and starts with none sold. A Ticket is either a StandardTicket or a VIPTicket; a VIPTicket adds a workshop seat. Draw the class diagram: associations with multiplicities read correctly in both directions, a generalization for the ticket kinds, and one operation with visibility and types.

Step 1: name the classes and the generalization

Attendee, Event, Ticket, StandardTicket, VIPTicket. "A VIPTicket is a Ticket with an extra" is generalization: an "is-a" relationship, drawn as a line with a hollow triangle pointing up to the more general class.

Step 2: draw the associations and read each end twice

Attendee "books" Ticket. Each Ticket is booked by exactly one Attendee → "1" at the Attendee end. An Attendee may book any number including none → "0..*" at the Ticket end. Event "offers" Ticket: each Ticket is for exactly one Event → "1" at the Event end; an Event starts with none sold and can have many → "0..*" at the Ticket end.

Step 3: fill the class boxes

Name, attributes, operations. Visibility markers: "+" public, "-" private. Attribute form "name: Type"; operation form "name(param: Type): ReturnType".

Full answer

Read both ends of each association aloud to check: each Ticket is booked by exactly one Attendee ("1" at the Attendee end), and an Attendee books zero to many Tickets ("0..*" at the Ticket end). Each Ticket is for exactly one Event ("1" at the Event end); an Event offers zero to many Tickets ("0..*" at the Ticket end).

The operation "+ cancel(): Boolean" is public, takes no parameters, and returns a Boolean. The attribute "- workshopSeat: String" on VIPTicket is private; the subclass keeps only what is specific to it, because it inherits the Ticket attributes and operations. That inheritance is the point of generalization in the lecture: common characteristics live in one place, so a proposed change does not force you to look at every class.

The trap: writing "0..*" at the Attendee end because the Attendee side looks "bigger". Multiplicity placement is not about importance; it counts instances at its own end. Also note the default: a multiplicity left off an association end means "1", so an unannotated diagram is still claiming exact ones everywhere.

Reasoning chain: classes and the is-a hierarchy → each association read in both directions → multiplicities at the correct ends → compartments filled with visibility and types → reread every end aloud.

Exercise 2 skill: reading a class diagram in both directions easy

Using the ConfTicket diagram above, answer: (a) How many Events can one Ticket be for? (b) How many Attendees can appear in one "books" link? (c) A colleague leaves both multiplicities off the "offers" association. What is the diagram then claiming? (d) For a cancelled VIPTicket, which class does the cancel() operation come from?

Step 1: read each end against its own class

Multiplicity at the Event end counts Events per Ticket. Multiplicity at the Attendee end counts Attendees per Ticket.

Step 2: apply the default

From the course's own answers deck: the default multiplicity is "1". Blank ends are claims, not gaps.

Step 3: apply inheritance

Subclasses inherit attributes and operations from their superclasses; lower-level classes may add more specific ones.

Full answer

(a) Exactly one. The "1" sits at the Event end.

(b) Exactly one. The "1" sits at the Attendee end: each Ticket is booked by exactly one Attendee.

(c) With both ends blank, the diagram claims each Ticket is offered by exactly one Event and each Event offers exactly one Ticket: the default multiplicity is "1". That silently forbids an Event from selling many Tickets, which contradicts the description. Blank is not neutral.

(d) Ticket. cancel() is declared on Ticket, and VIPTicket inherits it; VIPTicket adds workshopSeat. The trap is answering "both classes" or "VIPTicket because it is the concrete one". Inherited operations live in the superclass in the diagram.

Reasoning chain: end counts its own class → default "1" where the notation is silent → inheritance for operations.

Exercise 3 skill: drawing a sequence diagram from a description hard

RoomBook: "A student requests to book a room. The booking manager processes the request and checks availability with the room registry. If the room is free at that time, a confirmation is returned to the student; otherwise a clash message is returned." Draw the sequence diagram: actor, objects as "name: Class", lifelines, message styles, and the choice drawn with an alt combined fragment.

Step 1: list the participants and their lifelines

The actor: Student (stick figure). The objects: b: BookingManager, r: RoomRegistry. The object box carries "name: Class" because an object is an instance of a class. Each participant gets a vertical dashed lifeline.

Step 2: order the messages and pick the styles

Student calls the manager: "book (roomID, slot)": a synchronous call (solid line, filled arrowhead), because the student waits. The manager calls the registry: "check (roomID, slot)": also synchronous. The registry answers "available": a reply (dashed line, open arrowhead).

Step 3: draw the branch

"If... otherwise" is the alt combined fragment: a frame labeled "alt" in its top-left corner, a dashed separator between the two operands, and each condition in square brackets. One operand runs; that is what alt means.

Full answer

Reading order: top to bottom. The student waits while book() runs; the manager waits while check() runs; the reply lets the manager continue; then exactly one alt operand sends the outcome back.

The course's four common sequence-diagram mistakes, worth checking on any diagram you draw or read: incorrect execution occurrence (the activation bar must sit on the lifeline of the object that is executing, covering the time it handles the message); misplaced arrows (a call points at the receiver, a reply points back at the caller); incorrect message order (a receiver cannot answer a message before the call arrives); missing reply messages (a synchronous call that never gets a reply leaves the caller waiting forever on the page).

The trap: drawing "available" as a solid call with a filled arrowhead because "it carries data back". The style encodes who waits and what the message is: replies are dashed with open arrowheads. Second trap: putting the two outcome messages in sequence instead of in an alt fragment: that draws a world where the student gets a confirmation and a clash one after the other.

Reasoning chain: participants and lifelines → message order from the prose → style chosen by meaning → branch drawn as alt with bracketed conditions.

Exercise 4 skill: deriving a class diagram from a sequence diagram hard

The lecture derives class diagrams from sequence diagrams step by step. Apply it to the "Book room" diagram above: (1) identify the classes, (2) the methods with their types, (3) the attributes with their types, (4) the relationships, (5) the associations with multiplicities. Then draw the class diagram.

Step 1: classes come from the object boxes

Each object "name: Class" names its class. Here: BookingManager and RoomRegistry.

Step 2: methods come from the message labels

A call to an object is an operation on its class, with the message's parameters as operation parameters. Types are inferred from what the data is.

Step 3: attributes from what the objects keep

An object that answers questions about many things stores a collection of them. RoomRegistry answers check() about rooms; BookingManager answers book() about bookings.

Step 4: relationships and multiplicities

Objects that exchange messages are associated. Multiplicities come from the story the diagram tells: how many of each participate.

Full answer

1. Classes: BookingManager, RoomRegistry.

2. Methods: BookingManager "- book(roomID:int, slot:int): Boolean" (returns whether the booking was created); RoomRegistry "- check(roomID:int, slot:int): Boolean" (returns availability). The minus signs mark them private to their class in the lecture's own worked answer style; if you prefer these as the classes' public entry points, "+" is defensible; pick one and be consistent.

3. Attributes: BookingManager "bookings: List<bookingRef:String>": what it keeps to answer for existing bookings; RoomRegistry "rooms: List<roomID:int>": what it keeps to answer availability.

4. Relationship: the manager consults the registry, a plain association.

5. Multiplicities: the description shows one booking manager consulting one room registry, so "1" at each end. If the system were built with several booking managers sharing one registry, the registry end would still be "1" and the manager end "0..*". The multiplicities are a claim about the running system, so they must follow the story, not habit.

The trap: letting the alt fragment generate a class. "confirmation" and "clash message" are messages, not objects; only object boxes on lifelines become classes. A second trap: copying message names straight through without types: the lecture's worked answer takes the trouble to write "viewInfo(PID:int)", not "viewInfo".

Reasoning chain: object boxes → classes; message labels → typed operations; persistent state → attributes; message exchange → association; the story → multiplicities.

Exercise 5 skill: mixed (from requirement to use case to sequence) hard

This pulls in page 2 and page 3. For RoomBook's "Cancel booking" use case (tabulated on page 3: a student may cancel only more than one hour before the booking starts; within the final hour it stands), do the chain: (1) state what the sequence diagram must show that the tabular description already fixed; (2) draw the sequence diagram (Student, cm: BookingManager, rm: RoomRegistry); (3) name the class-diagram consequence.

Step 1: mine the tabular description for interaction facts

Actors: Student. Stimulus: cancel command naming a booking. Response: confirmation or refusal. Rule: the one-hour window, checked before the outcome. So the diagram needs a request, a check, and a branch on the check's result.

Step 2: draw the same shape as Exercise 3

Request (sync call), check (sync call), check result (reply), then alt on the result. The outcome messages are replies back to the student.

Step 3: translate back to structure

New message names imply new operations; a stored booking implies state.

Full answer

1. The description fixes: who acts (Student), what starts it (cancel command naming a booking), the guard rule (one hour), and the two outcomes (confirmation with the room released, or refusal). What it leaves to the diagram is the order: the rule must be evaluated before either outcome is sent.

For clarity the diagram elides one call that a fuller model would show: after "cancelled", the manager tells the registry to release the room, and the registry replies. The page 3 table says the room becomes available immediately, so a diagram for a design review should carry that call.

3. Class-diagram consequences: BookingManager gains "- cancel(bookingID:int): Boolean"; RoomRegistry gains "- startsIn(bookingID:int): int" (or whatever shape the system uses to answer about timing) and a release operation. The Booking objects (bookings the manager keeps in its list) now carry a state (booked, cancelled) and a start time, because the rule reads it. Structure follows interaction; that is why the lecture derives class diagrams from sequence diagrams.

The trap: hard-coding the one-hour rule as an alt condition on the actor's side, as if the student decides. The check belongs to the system's objects; the actor only supplies the command. Second trap: modelling "refused" as a silent nothing: the description demands a response in both branches.

Reasoning chain: extract interaction facts from the table → draw request, check, reply, alt → read the diagram back against the table → translate messages into operations and state.

Discuss

Take a position: "Deriving class diagrams from sequence diagrams, the way the lecture teaches, is backwards. Structure first, then interactions, or the class diagram just parrots whatever scenarios you happened to draw." Defend or attack. Evidence that would change your mind: project data showing one order consistently catches more modelling errors, or a case where a scenario-derived class diagram missed a structure that any domain-first approach would have found. The lecture's order exists because models communicate; argue whether that justifies it.
