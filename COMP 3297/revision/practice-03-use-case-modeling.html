Use case modeling: practice

Exercises on actors, use cases, associations, the system boundary, and use case descriptions that actually communicate. Diagram answers use the lecture's notation: stick figures with names below, names inside the ellipses, plain lines.

Background: Use case modeling.

Quiz

Q1

A teammate draws the actor-to-use-case associations with arrows showing who starts the interaction. What does the lecture say?

The lecture's answer to its own "common question 1" is exactly this: use case diagrams should use lines without arrows, because arrows in the UML indicate the direction of flow of messages. The trap is that arrows feel informative here. They import a meaning that belongs to sequence diagrams.

Q2

For a CampusBike lending kiosk, which of these is a valid actor?

Actors may be people or external systems. The payment gateway is external, so it qualifies, and the lecture draws even the external "Patient record system" as a stick-figure actor. The deposit module and the database are inside the system boundary, so they are not actors. "Borrow bike" is a use case: a discrete task involving external interaction.

Q3

What does a use case diagram alone NOT give you?

The lecture is blunt about this: use case diagrams give a simple overview of interaction, and more detail is needed for a complete interaction description: a simple textual description, a structured description in a table, or a sequence diagram. The diagram is an index into those descriptions, not a substitute.

Guided exercises

Exercise 1 skill: building a use case diagram from a brief medium

CampusBike is a self-service bicycle lending kiosk. Borrowers use it to take and return bikes. Faults can be reported by borrowers and inspected by technicians. Taking a bike requires a deposit, settled through the bank's payment gateway, an external system. Build the use case diagram: name the actors, name the use cases, and draw the associations.

Step 1: find the things outside the system that interact with it

People and external systems that pass information or commands across the boundary. Here: borrowers, technicians, and the bank's payment gateway. Everything the kiosk does internally (its deposit module, its bike database) is inside the boundary and is not an actor.

Step 2: name each use case as a discrete task with external interaction

The lecture's test: a use case represents a discrete task that involves external interaction with the system. Borrow a bike, return a bike, report a fault, pay a deposit. Not "manage the kiosk" (too big), not "validate card number" (an internal step of paying the deposit).

Step 3: connect each actor to the tasks it takes part in

Plain lines, no arrows. One task can involve more than one actor: reporting a fault involves the borrower who reports and the technician who inspects; paying the deposit involves the borrower and the payment gateway.

Full answer

Reading the diagram back against the brief: borrowers take part in all four tasks; technicians take part in fault inspection; the payment gateway takes part in settling the deposit. Nothing in the brief is missing, and nothing inside the kiosk leaked out as an actor.

On the system boundary: the diagram above does not draw a boundary box, matching the lecture's own use case diagrams. What matters is the decision, not the rectangle. Inside: the kiosk's deposit module, bike database, screen and lock hardware as the system implements them. Outside: borrowers, technicians, the bank. Moving that line has profound effects on the requirements: if the deposit module were bought in from the bank, "pay deposit" would become system-to-system interaction and the requirements for it would change. Defining the boundary is a political judgment, and it is one you should be able to defend.

The trap: drawing the payment gateway as an ellipse ("Process payment") inside the system instead of as an external actor. The gateway is a system you talk to, not a task the kiosk performs. The rule from the slide is short: actors may be people or external systems; use cases are discrete tasks involving external interaction.

Reasoning chain: classify what is outside the boundary → name discrete externally-observable tasks → associate each actor with each task it touches → check the picture against the brief.

Exercise 2 skill: writing a tabular use case description medium

RoomBook lets students book seminar rooms. Write the tabular description of the use case "Cancel booking" using the lecture's fields: Actors, Description, Stimulus, Response, Comments. The system's rules: a student may cancel any booking up to one hour before it starts; after that the booking stands and counts against the student's weekly quota; a cancelled room becomes available immediately.

Step 1: fix the field meanings from the lecture's example

Actors: who takes part. Description: what the interaction is. Stimulus: what starts it. Response: what the system does back. Comments: conditions and constraints, such as permissions. The lecture's 'Transfer data' table is the model: one row of fact per field, no design talk.

Step 2: put each fact in its field

The cancellation rules are the substance: they belong in Description (the main behaviour) and Comments (the conditions). The command the student issues is the Stimulus; what the system confirms is the Response.

Step 3: check the table against the use case diagram

The lecture's rule: the model should align with the description. If your diagram has "Cancel booking" associated with a Student actor and a Clerk actor, the table must name both actors too.

Full answer

RoomBook system: Cancel booking

ActorsStudent
DescriptionA student cancels an existing room booking. If the booking starts more than one hour from now, the cancellation succeeds and the room becomes available immediately. If it starts within an hour, the system refuses the cancellation and the booking stands.
StimulusCancel command issued by the student, naming a booking.
ResponseConfirmation that the booking is cancelled and the room released, or a refusal message when the one-hour rule applies.
CommentsRefused cancellations still count against the student's weekly quota. Only the student who owns the booking may cancel it.

The trap: writing the Description as a flow of screen interactions ("the student clicks Cancel, the dialog opens..."). The field wants what the interaction is, not how the screen is built. Screen detail is design, and it belongs to the prototype stage later in the pack (practice page 5). A second trap is burying the one-hour rule in Comments only; a reader who scans Description alone would build a system that always cancels.

Reasoning chain: fix field meanings → distribute the facts → verify the table against the diagram and the rules given.

Exercise 3 skill: checking a diagram against a description medium

The requirements say: "At the clinic, a receptionist calls patients into the consulting room. A nurse can mark a patient as a no-show. Patients check themselves in at the kiosk. Reminder texts are delivered through the SMS gateway, an external system." A colleague draws: one actor "Receptionist", connected by arrows to three ellipses ("Call patient", "Check in", and "SMS gateway"), plus a line from "Receptionist" to a fourth ellipse "Mark no-show". List everything wrong with that diagram, then draw it correctly.

Step 1: check the actors

Who crosses the boundary according to the text? Receptionists, nurses, patients, and the SMS gateway (an external system). The colleague has one actor where the text has four participants.

Step 2: check what counts as a use case

Each use case is a discrete task involving external interaction. "Call patient", "Check in", "Mark no-show" qualify. "SMS gateway" is a thing, not a task: it is an external system, so it is an actor.

Step 3: check the associations and the notation

Who performs each task? Call patient is the receptionist's; Mark no-show is the nurse's; Check in is the patient's; sending a reminder is a task involving the SMS gateway. And the arrows must go: the lecture's rule is plain lines.

Full answer

Four faults. (1) Nurse and Patient are missing as actors, though the text gives each their own interaction. (2) The SMS gateway is drawn as a use case; it is an external system, so it is an actor, the same class of mistake as treating the CampusBike payment gateway as a task. (3) Two tasks sit on the wrong actor: the text says the nurse performs "Mark no-show" and the patient performs "Check in", not the receptionist. (4) Arrows instead of plain lines: the trap, again: arrows carry message-flow meaning that belongs to sequence diagrams.

Reasoning chain: enumerate boundary-crossers as actors → classify each named thing as task or thing → reassociate by who performs the task → strip the arrows.

Exercise 4 skill: deciding when a use case diagram earns its place hard

A student project is a single screen where a user pastes text and presses one button to count words. The team has produced: a use case diagram with one actor and one ellipse, and a tabular description of the task. A second team builds a tutoring platform with three user classes (student, tutor, administrator), an external payment service, and a video tool. For each project: does the use case diagram earn its place, what should it show, and what does the diagram still not tell you?

Step 1: test what the diagram would add

A use case diagram's value is the overview of interaction: which actors, which discrete tasks, how they cross. With one actor and one task, the diagram repeats one sentence.

Step 2: apply it to the bigger system

Three user classes and two external systems, each touching several tasks: that is where the overview pays: missing actors and misassigned tasks become visible at a glance.

Step 3: state the standing limit

Whatever the size, the diagram is only an overview. Complete interaction description needs the text.

Full answer

Word counter: the diagram barely earns its place. One stick figure and one ellipse communicate nothing the sentence "the user pastes text and counts words" does not. The tabular description is the real deliverable. Draw the diagram anyway if the client wants a picture to nod at (the lecture notes models are used to communicate with customers), but do not pretend it adds information.

Tutoring platform: the diagram earns its place. It should show the three user classes as actors, the payment service and video tool as external-system actors, and one ellipse per discrete task (for example: book session, run session, pay for session, manage timetable, issue refund). Its payoff is exactly the errors Exercise 3 caught: missing actors and tasks attached to the wrong actor.

What it still does not tell you, in both cases: the order of interaction, the rules and conditions, the data. That is the lecture's point: the diagram gives a simple overview and must be supplemented by a textual description, a structured table, or a sequence diagram. The tabular description is where the one-hour cancellation rule from Exercise 2 could live; no ellipse could carry it.

Reasoning chain: measure the diagram by the overview it adds → apply to each system's actor and task count → restate the supplement rule regardless of size.

Exercise 5 skill: mixed (from interview to use case model) hard

This pulls in practice page 2. From an interview for RoomBook: "Students should be able to book a room, I mean they can pick a room and a slot and it's theirs unless a clash is found. Our two seminar rooms need the coordinator to approve the booking. Verifying their campus card at the door is done by the card system, not us." (1) Draw the use case model. (2) Write the tabular description of "Book room". (3) Write one user-requirement sentence from the quote, in the standard format. (4) Name one elicitation problem the quote shows.

Step 1: separate actors from tasks

Students (people), the coordinator (person), the card system (external system). Tasks with external interaction: book room, approve booking, verify card.

Step 2: distribute the rules to their places

The clash rule is system behaviour inside "Book room"; approval applies to the seminar rooms; card verification is a separate interaction with an external system.

Step 3: write the requirement and name the elicitation problem

The quote carries a self-correction ("I mean...") and a scope question (does every booking need approval or only the seminar rooms?).

Full answer

One judgment call worth naming: the quote says card verification is "done by the card system, not us", so a strict boundary reading drops "Verify card" from RoomBook's own use cases and treats the card system as an external service RoomBook relies on. The diagram above keeps "Verify card" as a task that crosses the boundary, with the card system as an actor; either reading is defensible, but the card system is never a use case.

2. RoomBook system: Book room. Actors: Student. Description: A student chooses a room and a time slot. If the room is free at that slot and the booking does not clash with the student's other bookings, the booking is created; for the two seminar rooms the booking is created with status "awaiting approval". If a clash is found, the booking is refused. Stimulus: Book command issued by the student, naming a room and slot. Response: Confirmation of the created booking (or its pending-approval status), or a clash message. Comments: Seminar-room bookings require the coordinator's approval before the room is held; other rooms are held immediately.

3. "The system shall let a student book a free room for a chosen time slot (rationale: booking is the service RoomBook exists to provide)." The clash rule becomes its own mandatory requirement: "The system shall refuse a booking that clashes with an existing booking for the same room."

4. The quote shows requirements in the stakeholder's own terms, with self-correction and an unstated scope decision. "I mean they can pick a room and a slot" is a restatement under pressure; "our two seminar rooms need approval" leaves open whether approval covers anything else. Fix it the way page 2 says: separate the strands, confirm each back in writing.

Reasoning chain: actors and tasks from the quote → rules into the tabular fields → one sentence per requirement → name the elicitation defect and the repair.

Discuss

Discuss

Take a position: "For a system with one actor and three tasks, the use case diagram adds nothing. Write the three tabular descriptions and skip the picture." Defend or attack. Evidence that would change your mind: documented cases where a one-actor diagram still caught a real modelling error, or a review process that demonstrably reads pictures before text. The lecture values models for communication with customers; argue where that value starts and stops.
