Class and sequence diagrams

The two UML workhorses: sequence diagrams show one interaction unfolding in time; class diagrams show what exists and how it relates. Notation is graded in this course, so this page states each convention exactly as the lecture draws it.

The mental model: a script and a cast list

Both diagrams model the same system, at different moments. A sequence diagram is the script of one performance: a particular use case running, participant by participant, message by message, from top to bottom. A class diagram is the cast list and the set of standing relationships: which kinds of object exist, what they know and do, and how they relate before anything runs.

Structural models "display the organization of a system in terms of the components that make up that system and their relationships", the lecture splits them into static models (structure of the design) and dynamic models (organisation while executing). Class diagrams belong to the object-oriented structural model: they show the classes in a system and the associations between them. Interaction models (use case plus sequence) sit alongside (see page 3). One use case's interaction overview is exactly what a sequence diagram supplies.

Learn the pair together. The lecture builds class diagrams from sequence diagrams step by step, and every message in a sequence diagram becomes an operation on some class. If you can read one, you can derive the other.

Source: L3 - Modeling to Communicate (UML-lite) v1.pdf, slides 40-43.

Sequence diagrams

"UML sequence diagrams model the interactions between the actors and the objects within a system. A sequence diagram shows the sequence of interactions that take place during a particular use case or use case instance." Time runs downward. The elements, numbered as the lecture annotates them:

  • Actor (1a): stick figure at the left, the external participant that starts the interaction.
  • Object (1b): a rectangle labelled name : Class, such as P: PatientInfo. The name is the instance name; "P is the instance of the class PatientInfo".
  • Lifeline (1c): the dashed vertical line below each participant, its existence over time.
  • Message (2a): a horizontal arrow between lifelines. The annotation (2b) carries the call detail: operation name, parameters, and return values, like report(Info, PID, UID).
  • Synchronous call (3a): solid line with a filled triangle arrowhead. "Sender must wait for a response to continue."
  • Reply message / asynchronous return (3b): dashed line with an open triangle arrowhead. Replies to an earlier call, like authorization.
  • Asynchronous call (3c): solid line with an open triangle arrowhead. "Without waiting for return value."
  • Execution occurrence (4): a thin rectangle on the lifeline while that participant is active.
  • Combined fragment (5): for alternatives, a frame labelled alt in its corner with compartments guarded by conditions in square brackets, such as [authorization OK] and [authorization fail]. "One of the contained interactions will be executed."

Read it as a story, top to bottom. The receptionist issues ViewInfo(PID) and waits (solid, filled arrow). PatientInfo calls the report engine, which calls the authorization component, both synchronous. Authorization replies with authorization (dashed, open arrow) back to the caller's execution occurrence. Then the alt frame splits the world in two: on success the patient information goes back to the receptionist; on failure an error does. Exactly one compartment runs.

The arrowheads are not decoration. A filled triangle is a claim that the sender blocks; an open triangle on a solid line is a claim that it does not; a dashed line is a claim that this message is a response. The lecture's later slide asks whether an asynchronous message is appropriate for a fire-and-forget logging call, and whether a return is even needed: the notation is a set of promises about behaviour, so choose it from the behaviour, not from habit.

Exam angle

The lecture's "Any problem(s)?" sequence is a notation audit with four named faults to look for: incorrect execution occurrence (a bar where the participant is not active, or no bar where it is), misplaced arrows (message starting or ending on the wrong lifeline), incorrect message order (a call drawn before the call that triggers it), and missing reply messages (a synchronous call with nothing coming back). Practise spotting these on unfamiliar diagrams. That is the exam skill.

Source: L3 - Modeling to Communicate (UML-lite) v1.pdf, slides 23-25, 26-38; the four common mistakes are named in L3 - Modeling to Communicate (UML-lite) v2 _Answers.pdf, slides 27-35.

Class diagrams

"A Class is a blueprint for an object": every object is built from the same blueprint and so carries the same properties and methods. An object is an instance of a class; in a sequence diagram the object P is an instance of class PatientInfo. The class diagram draws the blueprints.

Notation, item by item as the lecture annotates it:

  • Class: a box with up to three compartments: class name, attributes, operations (methods).
  • Visibility: + denotes public attributes or operations, - denotes private ones.
  • Attribute: name plus attribute type, like PID:int.
  • Operation: name plus parameter types plus return type, like -authorize(Info:String, UID:int).
  • Association: a solid line between classes, no arrowheads (navigation is not being claimed).
  • Multiplicity: a number or range at each end of the line, such as 1, 0..1, 1..*, 1..4. If it is missing, the default multiplicity is 1.
  • Association name and end names: a name for the relationship ("Involves") and optionally a name for each end describing that end's perspective ("referred-by").

Reading multiplicity without fooling yourself

The rule that makes every reading check out: a multiplicity counts objects of the class at its own end, per single object of the class at the other end. Then the lecture's examples fall out:

  • Patient record to Patient with 1 at both ends: each patient record maintains information about exactly one patient, and each patient has exactly one record. A 1:1 relationship.
  • Patient diagnosed-with Condition with 1..* at both ends: a patient may suffer from several conditions, and the same condition may be associated with several patients.
  • Consultation Involves Hospital doctor with 1..4 at the hospital doctor end: each consultation involves 1-4 hospital doctors. The 1..* at the consultation end reads the other way: a hospital doctor may be involved in several consultations.
  • 0..1 means optional: at most one, possibly none.

Aggregation, composition, and generalisation

Aggregation models how a "whole" object is composed of "part" objects, a "part of" / "has a" relationship. The hollow diamond sits at the whole end: a patient record is composed of a Patient and an indefinite number of Consultations. Standard UML draws one stronger variant the lecture's figure does not need: composition, a filled diamond, where parts share the whole's lifetime (delete the record and its consultations go with it). Use the hollow diamond unless you can defend the lifetime claim; the exam expects the diamond at the whole end either way.

Generalisation manages complexity by factoring shared characteristics upward: hospital doctors and general practitioners share what all doctors have. The arrow points up: a hollow triangle on a solid line, toward the more general class, forming an "is-a" relationship. Subclasses inherit attributes and operations from their superclasses and add their own: all doctors have name, phone, email, register(), de-register(); hospital doctors add staff number and pager; general practitioners add practice name and address. The stated advantage is change management: "if changes are proposed, then you do not have to look at all classes in the system to see if they are affected." In Java, generalisation is implemented with class inheritance.

Generalisation versus aggregation is the exam's favourite distinction. Generalisation is "is-a": a hospital doctor is a doctor; the subclass inherits everything. Aggregation is "has-a": a patient record has consultations; the parts keep their own classes and are referenced by the whole. The lecture's follow-up question (what changes at implementation time) has the honest answer: inheritance implements generalisation, while aggregation is implemented by references or collections.

And you can live without generalisation: the lecture's answer slide flattens the hierarchy by copying the shared attributes into each class. It works — until a shared attribute changes, and you edit every class. That is the trade generalisation buys you.

From sequence diagram to class diagram

The lecture's bridge between the two views is a five-step derivation, run on the 'View Patient Information' interaction you met above:

  1. Identify classes: the objects in the sequence diagram are your classes: PatientInfo, ReportEngine, Authorization.
  2. Identify methods and types: each message becomes an operation, with the annotation's parameter and return types: -viewInfo(PID:int), -report(Info:String, PID:int, UID:int), -authorize(Info:String, UID:int).
  3. Identify attributes and types: the data the operations work on: PID:int, Info:String, UID:int, and collections like reports: List.
  4. Define relationships: who talks to whom across the interaction.
  5. Draw associations and multiplicity: the worked derivation lands on multiplicities like 0..* and 1 between the three classes, read by the per-object rule above.

The reverse direction works too: the lecture notes that the overview of interaction for each use case can be presented by a sequence diagram, so a class diagram's associations suggest which interactions are possible. Keep the two consistent, the way the use case diagram must stay consistent with its description.

Tooling

Text-based UML: you type the diagram, the tool draws it. Mermaid supports class and sequence diagrams (and state diagrams) and renders directly in GitHub Markdown, so a repository shows up to date diagrams with no plug-ins and no image files. It works with Git: version control, diff, code review. But always review AI-generated diagrams against the user stories, the notation, and your other diagrams: "AI makes the same mistakes you saw today, only faster".

Q1

On a sequence diagram, a message drawn as a solid line with an open (hollow) triangle arrowhead means:

The lecture's three-way convention: synchronous call = solid line, filled triangle (sender waits); reply or asynchronous return = dashed line, open triangle; asynchronous call = solid line, open triangle (sender does not wait). The line style separates calls from replies; the arrowhead fill separates blocking from non-blocking.

Q2

In a class diagram, Consultation is connected to Hospital doctor by an association labelled "Involves" with multiplicity 1..* at the consultation end and 1..4 at the hospital doctor end. Which reading is correct?

A multiplicity counts objects at its own end, per one object at the other end. So 1..4 at the hospital doctor end says how many doctors per consultation, which is exactly the lecture's annotation, and 1..* at the consultation end says how many consultations per doctor.

Discuss

Take a position: on an exam class diagram, any association with both multiplicities greater than 1 is a modelling smell that should be resolved into an association class or a new class. Evidence that would change your mind: a domain where a genuine many-to-many relationship needs no extra artefact to stay understandable and implementable.

Discuss

Take a position: the lecture's four sequence-diagram faults (execution occurrence, misplaced arrows, message order, missing replies) are all really one fault: the diagram disagrees with the description. Evidence that would change your mind: a diagram that matches its description perfectly and is still wrong in one of the four named ways.

Can you yet?

  • Label every part of a sequence diagram: actor, object box naming, lifeline, message, execution occurrence, alt fragment.
  • Distinguish the three message line-and-arrowhead combinations (sync call, reply, async call) and say what each promises about waiting.
  • Name the four common sequence diagram faults and spot one in a worked example.
  • Read any multiplicity (1, 0..1, 1..*, 1..4) with the per-object rule and say what the default is when it is missing.
  • Draw class boxes with name/attributes/operations compartments, +/- visibility, and typed attributes and operations.
  • Tell aggregation (hollow diamond, "has-a") from generalisation (hollow triangle up, "is-a") and from composition (filled diamond), and say what each implies in code.
  • Derive a class diagram skeleton from a sequence diagram in the five steps.
