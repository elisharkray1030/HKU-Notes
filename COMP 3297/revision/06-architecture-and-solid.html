Architecture and SOLID

The decisions that are expensive to reverse, at two scales: the architecture that organises a whole system, and the SOLID principles that keep individual classes changeable. Both exist for the same reason — software inevitably changes.

The mental model: the expensive decisions

Architectural design is "understanding how a software system should be organized and designing the overall structure of that system". The lecture calls it "the critical link between design and requirements engineering", because it identifies the main structural components and the relationships between them. Its output is an architectural model: how the system is organised as a set of communicating components.

Two facts justify the whole topic. First, "refactoring the system architecture is usually expensive because it affects so many components in the system", which is why even agile processes design an overall architecture at an early stage. Second, architecture lives at two scales: architecture in the small (how one program decomposes into components) and architecture in the large (enterprise systems spanning systems, programs and components, distributed across machines possibly owned by different companies).

What you get for making the architecture explicit: stakeholder communication (a focus for discussion), system analysis (you can check whether the system can meet its non-functional requirements, the payoff of the measurement work on page 2), and large-scale reuse (the architecture may be reusable across a range of systems).

How it is drawn: box and line diagrams: "simple, informal block diagrams showing entities and relationships". A box is a component; boxes within boxes are subcomponents; arrows are data or control signal flow. They are very abstract but useful for communication with stakeholders and for project planning. The lecture notes the standing criticism: these diagrams lack semantics. They show that things talk; they do not say what the talk means.

Source: L5a - Design - Architecture Patterns and SOLID v1.pdf, slides 3-7.

Architectural design decisions

Architectural design is creative and varies by system type, but common decisions span all design processes, and "these decisions affect the non-functional characteristics of the system". The lecture's eight:

  1. Is there a generic application architecture that can act as a template for the system being designed?
  2. How will the system be distributed across hardware cores or processors?
  3. What architectural patterns or styles might be used?
  4. What will be the fundamental approach used to structure the system?
  5. How will the structural components be decomposed into sub-components?
  6. What strategy will be used to control the operation of the components?
  7. What architectural organization is best for delivering the non-functional requirements?
  8. How should the architecture of the system be documented?

Architecture reuse makes decision 1 practical: systems in the same domain often have similar architectures reflecting domain concepts; application product lines are built around a core architecture with variants for particular customers (the lecture's example: Microsoft 365); and an architecture can be designed around one or more architectural patterns or styles, which "capture the essence of an architecture and can be instantiated in different ways".

Source: L5a - Design - Architecture Patterns and SOLID v1.pdf, slides 8-11.

Quality attributes and trade-offs

Decision 7 is where architecture earns its keep, and the lecture gives a tactic per characteristic:

  • Performance: localise critical operations and minimise communications. Use large rather than fine-grain components.
  • Security: use a layered architecture with critical assets in the inner layers.
  • Safety: localise safety-critical features in a small number of sub-systems.
  • Availability: include redundant components and mechanisms for fault tolerance.
  • Maintainability: use fine-grain, replaceable components.

Now spot the collision. Performance wants large components and minimal communication; maintainability wants fine-grain components you can replace. You cannot maximise both: this is the lecture's open-floor question ("Do you find any potential conflict to achieve these five system characteristics at the same time?") and its benchmark follow-up (a single-level design versus a nested-levels design, in the spirit of "clean code versus performance"). Clean structure costs call overhead; monolithic speed costs replaceability. The mature answer is not "pick one forever" but "know which one this system is paying for, and record why": that recording is decision 8.

Discuss

Take a position: for a booking system whose peak load one day a year is 50 times normal, the performance tactic (large components, minimal communication) should win over the maintainability tactic (fine-grain replaceable parts). Evidence that would change your mind: the actual cost of the peak-day failure versus the year-round cost of slower change: one incident report or one maintenance time sheet beats intuition here.

Architectural patterns

"Patterns are a means of representing, sharing and reusing knowledge. An architectural pattern is a stylized description of good design practice, which has been tried and tested in different environments." The lecture's demand on a pattern: it should say when it is and when it is not useful. Four in the course, each in the same four-part shape.

Model-View-Controller (MVC)

Description: separates presentation and interaction from the system data, structured into three logical components that interact. When used: multiple ways to view and interact with the data; future requirements for interaction and presentation are unknown. Advantage: the data can change independently of its representation, and vice versa. Disadvantage: additional code and code complexity.

Layered architecture

Description: organises the system into layers with related functionality; lowest-level layers represent core services. When used: building new facilities on top of existing systems; each team responsible for a layer; multi-level security. Advantages: entire layers can be replaced so long as the interface is maintained; redundant facilities (e.g. authentication) can be provided in each layer to increase dependability. Disadvantages: clean separation is often difficult; a high-level layer may have to interact directly with lower layers rather than only with the one below; performance suffers from "multiple levels of interpretation of a service request as it is processed at each layer". The lecture's own example: the iLearn system architecture.

Repository

Description: all data is managed in a central repository; components do not interact directly, only through the repository. When used: large volumes of information generated and stored for a long time; data-driven systems where inclusion of data triggers an action or tool. Advantages: components can be independent; changes made by one component propagate to all; all data managed consistently in one place. Disadvantages: the repository is a single point of failure; organising all communication through it may be inefficient; distributing it across several computers may be difficult. Example: a repository architecture for an IDE.

Client-server

Description: functionality organised into services, each delivered from a separate server. When used: data in a shared database accessed from a range of locations; because servers can be replicated, also when load is variable. Advantages: servers can be distributed across a network; general functionality (e.g. printing) available to all clients. Disadvantages: each service is a single point of failure (the lecture names DDoS and server failure); performance may be unpredictable because it depends on the network; management problems if servers are owned by different organisations.

Exam angle

Pattern questions almost always come as "which pattern fits this system, and what do you give up?" The selection half is the "when used" clause; the trade-off half is the disadvantages list. Choosing layered for a multi-level security system and naming "clean separation is difficult and every layer adds interpretation cost" is a complete answer.

Source: L5a - Design - Architecture Patterns and SOLID v1.pdf, slides 16-21.

SOLID: five ways to keep change cheap

The summary slide gives the reason for the whole acronym: "Software inevitably changes/evolves over time (maintenance, upgrade)." SOLID is five principles for surviving that. Learn each as statement, mechanism, and the lecture's named example and smell.

Single Responsibility Principle (SRP)

"A class should have only one reason to change." A class should concentrate on doing one thing and one thing only. The habit: every time you create or change a class, ask how many responsibilities it has. The lecture's example: a Modem interface with dial, hangup, send, recv carries two responsibilities (connection management and data communication) and the smell is rigidity. The fix splits it into Connection and DataChannel. The caution is as important as the rule: if the application is not changing in ways that create those two responsibilities, no need to separate them. Otherwise the smell is needless complexity.

Java
// BAD: two responsibilities in one interface
interface Modem {
  public void dial(String pno);
  public void hangup();
  public void send(char c);
  public char recv();
}

// GOOD: one responsibility each
interface DataChannel {
  public void send(char c);
  public char recv();
}
interface Connection {
  public void dial(String pno);
  public void hangup();
}

Open-Closed Principle (OCP)

"Software entities (classes, modules, functions, etc.) should be open for extension, but closed for modification." Applied well, further changes of that kind are achieved by adding new code, not by changing old code that already works. The lecture's mechanism: build classes so you extend them through child classes and inheritance; once created, the class no longer needs to change. Its example: a PaymentManager with an enum and an if/else chain makes adding "Check" payment impossible without modifying PaymentManager, and adding a payment means hunting down every such switch statement. The fix: a Payment base class with pay(), and Cash, CreditCard, Check subclasses that override it.

C#-style (as in the lecture)
// BAD: extension requires modification
public enum PaymentType { Cash, CreditCard }
public class PaymentManager {
  public PaymentType PaymentType { get; set; }
  public void Pay(Money money) {
    if (PaymentType == PaymentType.Cash) { /* pay with cash */ }
    else { /* pay with credit card */ }
  }
}

// GOOD: open for extension, closed for modification
public class Payment {
  public virtual void pay(Money money) { /* base class */ }
}
public class Cash : Payment {
  public override void pay(Money money) { /* pay with cash */ }
}
public class CreditCard : Payment {
  public override void pay(Money money) { /* pay with credit card */ }
}

Liskov Substitution Principle (LSP)

The formal statement: "If for each object o1 of type S there is an object o2 of type T such that for all programs P defined in terms of T, the behavior of P is unchanged when o1 is substituted for o2 then S is a subtype of T." The working phrase: subtypes must be substitutable for their base types. The lecture's example: a Bird class with flySpeed and a Penguin subclass that cannot fly: the "is-a" wording survives ("a penguin is a bird") but substitutability does not (a program using flySpeed breaks when handed a penguin). The fix: capabilities as interfaces (CanFly and CanSwim) with Eagle taking fly speed and Penguin taking swim speed, both extending the base Bird that only holds what all birds share. Any functionality expected from the base type must be fulfilled by the subtype.

Interface Segregation Principle (ISP)

"Many specialized interfaces are better than one universal", or "Clients should not depend on methods that they do not use." The example: a Worker interface with work() and eat() forces RobotWorker to implement an eat() that is "not applicable": the interface is polluted, and the smell is needless complexity. The fix: Workable and Feedable; ManWorker implements both, RobotWorker only Workable. Keep interfaces as small as possible to avoid unnecessary dependencies; ideally any part of the code should be understandable in isolation.

Dependency Inversion Principle (DIP)

Two clauses: "High-level modules should not depend on low-level modules. Both should depend on abstractions." and "Abstractions should not depend on details. Details should depend on abstractions." The example: a DataHandler that constructs a concrete FilesystemStorage inside itself: the dependency is transitive, so DataHandler is sensitive to changes all the way down. The fix: a Storage protocol with save(), implemented by FilesystemStorage and CloudStorage, and DataHandler receives a Storage through its initialiser. Decoupled by formalising the communication interface around the needs of the higher-level class.

Swift-style (as in the lecture)
// BAD: high-level class depends on a concrete low-level class
class DataHandler {
  let storage = FilesystemStorage()   // dependency is transitive
  func handle(_ data: Data) { storage.save(data) }
}

// GOOD: both depend on the abstraction
protocol Storage { func save(_ data: Data) }
class DataHandler {
  let storage: Storage
  init(storage: Storage) { self.storage = storage }
  func handle(_ data: Data) { storage.save(data) }
}
let handler = DataHandler(storage: CloudStorage())

The lecture adds the "depend on abstractions" checklist: no variable should hold a pointer or reference to a concrete class; no class should derive from a concrete class; no method should override an implemented method of its base classes, with the standing exceptions like Java's String. And the ownership picture: naive layering has high layers owning low layers; inverted layers have both pointing at abstractions ("inversion of ownership").

Pitfall

The two named smells are diagnostic, and mixing them up loses marks. Rigidity means the class resists the kind of change the application actually makes (two responsibilities pulling it apart). Needless complexity means you split or abstract something the application never changes around. SRP and ISP are where the lecture names both: the principles are about the change you can predict, not about elegance.

Source: L5a - Design - Architecture Patterns and SOLID v1.pdf, slides 22-43.

Why SOLID matters more with AI

The lecture's closing claim: "AI writes code fast - structure is what keeps it testable and changeable." SRP keeps AI-generated classes small enough to review and unit-test; DIP is what makes code testable in isolation; OCP is what makes a project change request cheap — extend, do not rewrite (the course promises you will feel this after Client Meeting #2).

Source: L5a - Design - Architecture Patterns and SOLID v1.pdf, slide 44.

Q1

A system must satisfy multi-level security, with each team owning one tier of functionality. Which pattern does the lecture's "when used" clause point to, and what is its named performance cost?

"Multi-level security" and "each team responsible for a layer" are both in the layered pattern's when-used list, and its stated disadvantage includes performance problems from multiple levels of interpretation of a service request. Repository and MVC have different named costs that do not match the scenario.

Q2

A class handles invoice formatting and also opens the SMTP connection that sends the invoice. Which SOLID principle is primarily violated, and what is the lecture's named smell?

The Modem example is exactly this shape: connection management plus data communication in one place is two responsibilities, and the lecture names the resulting smell rigidity. Depending on a concrete class would additionally violate DIP, but the primary fault the question describes is the responsibility count.

One position worth arguing somewhere: the repository pattern is a poor default for a new web application in 2026, because the single-point-of-failure and distribution disadvantages outweigh its consistency advantage. Evidence that would change your mind: a system with a measured consistency or propagation requirement that only a central repository met within budget.

Discuss

Take a position: the lecture's SRP caution (separating responsibilities that never change is needless complexity) means a student project should deliberately ignore SOLID until the second change request. Evidence that would change your mind: the cost curve of your own project: if the first change request already cost more than the upfront structure would have, the position fails.
