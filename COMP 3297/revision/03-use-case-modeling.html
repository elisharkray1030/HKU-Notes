Use case modeling

Actors, use cases, associations, and the system boundary: the notation the lecture uses, and the discipline of making a diagram and its written description say the same thing. Notation errors here lose marks even when your understanding is right.

The mental model: a map of conversations

System modeling is developing abstract models of a system, each presenting a different view, using graphical notation: "now almost always based on notations in the Unified Modeling Language (UML)". Two audiences: models help the analyst understand the functionality, and they communicate with customers.

The lecture sorts diagrams into perspectives: context models model the environment (and are not UML), interaction models cover what passes between the system and its environment or among components (use case and sequence diagrams), structural models cover organisation of the system and its data (class diagrams), and behavioral models cover dynamic response to events (state machines). This page is one slice of the interaction perspective.

Two kinds of model, two jobs. Models of the existing system are used during requirements engineering to clarify what it does and to discuss strengths and weaknesses: these lead to requirements for the new system. Models of the new system explain proposed requirements to stakeholders, discuss design, and document for implementation. The lecture marks the first kind "may be incomplete" and the second "close to complete" for a reason: you model the old system only as far as you need to argue about the new one.

A use case diagram is the smallest useful map of the system's conversations. Each oval is one discrete task the system performs through external interaction; each stick figure is someone (or something) outside that takes part. The picture answers "who talks to this system, and about what?" — nothing more. Everything about how the conversation goes lives in a written description, and the lecture is explicit: "Use case diagrams give simple overview of interaction. We need to add more details for complete interaction description."

Source: L3 - Modeling to Communicate (UML-lite) v1.pdf, slides 3-11.

The notation, exactly as the lecture draws it

Three elements carry the whole diagram. The lecture annotates them by number:

  • Actor: a stick figure. Actors "may be people or external systems": the Mentcare example has a medical receptionist (a person) and the patient record system (another system), both drawn as stick figures.
  • Use case: an oval with the task name inside, for example "Transfer data". Each use case "represents a discrete task that involves external interaction with a system".
  • Association: a plain straight line from an actor to a use case. No arrowhead.

Three things this figure shows that students often get wrong:

  • An external system is an actor and gets the same stick figure as a person. The patient record system is outside this system, so it is an actor.
  • Not every actor touches every use case. The receptionist uses all five; the patient record system takes part only in "Transfer data". Drawing a line "because it exists" invents a requirement.
  • Multiple use cases and multiple actors are fine: a system has as many use cases as it has discrete external-interaction tasks.
Pitfall

Arrows on use case associations are wrong, and the reason is the whole discipline in one line: "Formally, use case diagrams should use lines without arrows because arrows in the UML indicate the direction of flow of messages." The moment you draw an arrow you are claiming a message flow, which is a different diagram. If the exam asks whether an arrow can replace the line, the answer is no, with that rationale.

Source: L3 - Modeling to Communicate (UML-lite) v1.pdf, slides 12-13; the arrow rule is stated in L3 - Modeling to Communicate (UML-lite) v2 _Answers.pdf, slide 15.

Where the system boundary sits

Context models show what lies outside the system, and system boundaries "define what is inside and what is outside the system". The lecture's warning: "The position of the system boundary has a profound effect on the system requirements", and defining it "is a political judgment". Move authentication outside the boundary and someone else owns it; move it inside and you just signed up for a security requirement.

One notation note, since the exam grades notation. The lecture's own use case figures draw actors and ovals with plain lines and no enclosing rectangle. Standard UML permits a boundary rectangle named after the system, with use cases inside and actors outside; if you draw one, name it and keep actors outside. What is never negotiable is the association: plain line. Include and extend relationships (dashed arrows carrying <<include>> / <<extend>>) and comments on elements are listed in the lecture as required reading (uml-diagrams.org) rather than taught notation: know they exist and what they are for (factoring out shared behaviour, optional behaviour), but the graded core is actor, oval, plain association.

Source: L3 - Modeling to Communicate (UML-lite) v1.pdf, slides 8-9, 18, 21.

Writing use cases that communicate

The diagram is the index; the description is the content. The lecture shows two levels: a simple textual description, and a structured description in a table. The tabular form for a Mentcare use case has these rows:

  • Actors: who takes part.
  • Description: what happens, in prose.
  • Stimulus: what starts it (a user command, an event).
  • Response: what the system returns or does.
  • Comments: conditions and caveats, such as permissions.

Worked example: View Patient Information

  • Actors: Medical receptionist.
  • Description: "A medical receptionist requests to view patient information. The request is processed through the report engine, which verifies the receptionist's authorization to access the information via the authorization component. If authorization is granted, the patient information is displayed; otherwise, an error message is returned."
  • Stimulus: ViewInfo command issued by the medical receptionist.
  • Response: Display of patient information or an error message indicating no access.
  • Comments: The receptionist must have appropriate security permissions to access the patient information. Authorization is required to ensure secure access.

Read that table and you already know the shape of its sequence diagram: a request in, a check with an authorization component, a branch into success or error. That is the point of the lecture's slide asking whether the diagram "aligns with the description": the two artefacts are two views of one truth, and a mismatch in either is a bug in your model. The 'Transfer data' table makes the same demand: the diagram must match rows like "Stimulus: user command issued by medical receptionist" and "Response: confirmation that PRS has been updated".

Check habit

After drawing any use case diagram, pick one oval and say aloud who the actors are, what starts it, and what comes back. If the picture does not let you answer all three, the picture is wrong or the description is missing.

Source: L3 - Modeling to Communicate (UML-lite) v1.pdf, slides 20, 23-25.

When a use case diagram earns its place

Use cases began as a requirements-elicitation tool and were later absorbed into the UML: keep that history in mind. The diagram earns its place when a reader needs the overview: a customer checking you have captured every task, a team agreeing on scope, an examiner seeing you know which actor touches which service. It loses to other artefacts when the question is about behaviour: the lecture hands each use case's interaction overview to a sequence diagram (page 4), and the detailed step-by-step behaviour to textual or tabular descriptions.

A practical way to decide: if removing the diagram would not change a decision anyone makes, it is decoration. The Mentcare figure changes decisions: "Contact patient" has no external system actor, so no interface work is scheduled; "Transfer data" does, so there is an integration requirement with the patient record system.

Pitfall

Mermaid has no use case diagram. It supports class, sequence and state diagrams, but ask an AI tool for a Mermaid use case diagram and "it will still give you a fake one" (the lecture's words, from the W3 walkthrough). Text-based UML is great for the diagrams Mermaid supports because it works with Git; for use cases, draw them and check them by hand.

Source: L3 - Modeling to Communicate (UML-lite) v1.pdf, slides 11-12, 22, 70.

Q1

A teammate draws the Transfer data use case with an arrow from the medical receptionist to the "Transfer data" oval, to show who starts it. Your review comment is:

The lecture's formal answer is that use case diagrams use lines without arrows, because in UML an arrow is a claim about message flow direction. Who initiates the task is written in the use case description's Stimulus row, not drawn as an arrow.

Q2

In the Mentcare use case diagram, the patient record system is drawn as:

The lecture draws both the medical receptionist and the patient record system as stick figures: "Actors in a use case may be people or external systems." What matters is that the entity is outside the boundary of the system being modelled, not what shape it is in real life.

Discuss

Take a position: for a system with fewer than ten use cases, the written descriptions alone are enough and the diagram should be dropped from the documentation. Evidence that would change your mind: a decision on a real project that the diagram made faster or more correct than prose alone, or a review comment that only the diagram caught.

Discuss

Take a position: putting the password service (authentication) inside your system boundary is the right call for a student project. Evidence that would change your mind: the cost of owning it: the security requirements you inherit, versus the cost and risk of depending on an external identity provider you do not control.

Can you yet?

  • Draw a use case diagram with correct notation: stick-figure actors, named ovals, plain-line associations, no arrowheads.
  • Say why a use case association must not carry an arrow, using the message-flow rationale.
  • Decide for a given entity whether it is an actor, and justify it by the system boundary rather than by whether it is a person.
  • Fill the tabular use case form (Actors, Description, Stimulus, Response, Comments) for a fresh task and check the diagram matches it.
  • Explain why the system boundary is a political judgment and give one requirement that moves when the boundary moves.
  • State when a use case diagram earns its place, and what artefact replaces it when it does not.
