Architecture and SOLID: practice

Exercises on architectural decisions and their trade-offs, choosing among the lecture's patterns, and spotting then fixing SOLID violations. The skill being trained: reading a requirement or a piece of code and naming the structural consequence.

Background: Architecture and SOLID.

Quiz

Q1

Which pair of system characteristics pulls the architecture in opposite directions?

The lecture's guidance states both sides: performance: localise critical operations and minimise communications, use large rather than fine-grain components; maintainability: use fine-grain, replaceable components. Large-and-local versus fine-and-replaceable is a direct clash, and the lecture's open-floor question asks exactly for such conflicts. The benchmark slides (single level vs nested levels) show the same tension in code.

Q2

All data in a system is managed in one central store, and components do not interact directly, only through that store. Which pattern is this, and which disadvantage comes with it?

The description is the repository pattern's own definition. Its stated disadvantages: the repository is a single point of failure, there may be inefficiencies in organising all communication through it, and distributing it across several computers may be difficult. The "clean separation" disadvantage belongs to layered architecture; "additional code" belongs to MVC.

Q3

A Worker interface declares work() and eat(). RobotWorker implements work() but its eat() is a no-op marked "not applicable". Which SOLID principle does this violate?

This is the page's deliberate trap. The lecture's own example is this Worker case, and it files it under ISP with the labels "polluted interface" and "smell of needless complexity". It looks like SRP because "two responsibilities" is the phrase that comes to mind, but the harm is clients depending on methods they do not use. The lecture's fix splits the interface into Workable and Feedable, so ManWorker implements both and RobotWorker implements only Workable.

Q4

Which is a stated disadvantage of the MVC pattern?

MVC's advantage is the reverse of the wrong option: it allows the data to change independently of its representation and vice versa. It is used precisely when multiple ways to view and interact with the data exist or future interaction requirements are unknown. The cost is extra code and complexity. "Single point of failure" is the repository's.

Guided exercises

Exercise 1 skill: reading quality attributes as architectural pressure medium

CityCare controls infusion pumps on hospital wards. Its requirements: it must never deliver the wrong dose; it must run around the clock; nurses must be able to roll out updated drug libraries without a developer; responses to pump alarms must be within 100 ms. For each requirement, name the architectural guidance the lecture gives, and state where the guidance conflicts.

Step 1: map each requirement to a characteristic

Wrong dose: safety. Around the clock: availability. Drug libraries without a developer: maintainability. 100 ms alarms: performance.

Step 2: pull the lecture's guidance for each

Safety: localise safety-critical features in a small number of sub-systems. Availability: include redundant components and mechanisms for fault tolerance. Maintainability: use fine-grain, replaceable components. Performance: localise critical operations and minimise communications; use large rather than fine-grain components.

Step 3: find the conflict and decide

Large-and-local versus fine-and-replaceable. For this system, which requirement loses first?

Full answer

Wrong dose: safety: localise the dosing logic in a small number of sub-systems, so it can be scrutinised and verified as a unit. Around the clock: availability: redundant components and fault tolerance, so a failed pump or server does not stop care. Drug libraries: maintainability: fine-grain, replaceable components, so the library can be swapped without touching dosing. 100 ms alarms: performance: localise the critical operation (the alarm path) and minimise communications.

The conflict is the lecture's own: performance asks for large, localised components with few messages; maintainability asks for fine-grain, replaceable ones. More replaceable pieces means more communication between them, which is exactly what the performance guidance warns against. The safety and availability guidance pulls toward isolating and duplicating the dosing sub-system, which also raises the cost of the frequent changes maintainability is protecting.

Decision for this system: safety and the 100 ms alarm path win. Keep the dosing and alarm components large, localised, and redundant; spend the maintainability budget where changes are actually frequent: the drug library, as a data pack or a replaceable component behind a fixed interface. The point of naming the trade-off is that somebody chooses which characteristic bends; the lecture's question is whether you can achieve all five at once, and the honest answer for this system is no.

Reasoning chain: requirement → characteristic → lecture's guidance → conflict named → explicit choice with the reason.

Exercise 2 skill: choosing an architectural pattern medium

Pick the pattern from the lecture for each scenario and name one disadvantage you accept with it. (a) A photo editor where plugins (export tools, filters, colour pickers) must all react whenever the image data changes. (b) A fitness product whose activity data must be shown on a phone app, a web dashboard, and a watch, with more views expected later. (c) A university portal being extended on top of its existing systems, with one team per layer of functionality and access controlled at several levels.

Step 1: match each scenario to a "when used" clause

Repository: large volumes of information stored for a long time, or data-driven systems where the inclusion of data triggers an action or tool. MVC: multiple ways to view and interact with the data, future interaction requirements unknown. Layered: building new facilities on top of existing systems, one team per layer, multi-level security.

Step 2: name the disadvantage that clause drags in

Each pattern's disadvantage is stated in the same slide as its use. Do not stop at naming the pattern.

Step 3: check the trap scenario

Scenario (a) is data-driven: tools triggered by data. That is repository territory even though "editor" sounds interactive.

Full answer

(a) Repository. The image data is the central store, and its changes trigger the tools, matching the lecture's "data-driven systems where the inclusion of data triggers an action or tool", like its IDE example. Accepted disadvantages: the repository is a single point of failure; routing all communication through it may be inefficient; distributing it may be difficult.

(b) MVC. Multiple views of the same data with unknown future interaction, which is the lecture's "when used" almost word for word. Accepted disadvantage: additional code and code complexity. The advantage you buy: the data changes independently of its representation and vice versa.

(c) Layered architecture. New facilities on existing systems, one team per layer, multi-level security (the security guidance even says to use a layered architecture with critical assets in the inner layers). Accepted disadvantages: clean separation between layers is often difficult; a high-level layer may have to interact directly with lower-level layers; performance may suffer from multiple levels of interpretation of each service request.

The trap: case (a). "Editor" suggests interactivity and pushes you to MVC. The deciding fact is what triggers the work: data change triggers every tool. Also note the lecture's rule about patterns: a pattern should include when it is and when it is NOT useful, so always state the disadvantage you are accepting.

Reasoning chain: scenario facts → the pattern's "when used" clause → the matching disadvantage → boundary case checked against the trigger.

Exercise 3 skill: spotting and refactoring SOLID violations hard

Two fragments from a reporting module. Name the violated principle in each and show the fix in the lecture's style.

Java
public class ReportManager {
    public String format(String data) { /* build the report text */ }
    public void saveToFile(String report) { /* write to disk */ }
    public void emailToClient(String report) { /* send via SMTP */ }
}
Java
public enum ReportType { PDF, CSV }

public class ReportExporter {
    public ReportType type;
    public void export(String report) {
        if (type == ReportType.PDF) {
            // build a PDF
        } else {
            // build a CSV
        }
    }
}
Step 1: count the reasons to change in ReportManager

Formatting changes when the report layout changes. Saving changes when storage changes. Emailing changes when the mail service changes. Three responsibilities, three reasons to change.

Step 2: find the extension trap in ReportExporter

Adding a new type means adding a branch here. The lecture's payment example is this shape: adding a new payment method means hunting for every switch statement and adding the new case to each.

Step 3: apply the fixes and the lecture's caution

SRP: separate the responsibilities and compose. OCP: make the changeable parts subclasses behind a fixed interface.

Full answer

ReportManager violates SRP: "a class should have only one reason to change." Three responsibilities, so the class is a smell of rigidity, like the lecture's Modem interface, which mixed connection management (dial, hangup) with data communication (send, recv). Fix, in the lecture's shape: split and compose.

Java
public interface DataChannel {
    void send(char c);
    char recv();
}

public interface Connection {
    void dial(String pno);
    void hangup();
}

For ReportManager the same move gives ReportFormatter, ReportStore, and MailSender, with ReportManager kept as a thin composer if anything still needs to coordinate them. The lecture's summary states the general shape: if class A has two responsibilities, create B and C to handle each in isolation, then compose A out of B and C.

ReportExporter violates OCP: "software entities should be open for extension, but closed for modification." Adding XLSX means modifying export(); a change of that kind should be achieved by adding new code, not by changing old code that already works. Fix: put the parts likely to change into implementations and define the interface around the parts that are unlikely to change.

Java
public abstract class ReportFormat {
    public abstract void export(String report);
}

public class PdfFormat extends ReportFormat {
    public void export(String report) { /* build a PDF */ }
}

public class CsvFormat extends ReportFormat {
    public void export(String report) { /* build a CSV */ }
}

Now XLSX is one new class. The switch is gone; the working export code is untouched.

Two traps. First: "closed for modification" does not mean the class is frozen forever. It means further changes of that kind arrive as new code. Second: the lecture's caution on SRP: if the application is not changing in ways that create the two responsibilities, splitting is needless complexity. Ask how many responsibilities the class has and whether those responsibilities actually change; both matter.

Reasoning chain: reasons to change → SRP check → split and compose; extension scenarios → OCP check → hierarchy behind a fixed interface; both checked against the lecture's cautions.

Exercise 4 skill: naming the principle from a symptom medium

Name the principle involved in each case. (a) A Penguin object is passed where callers expect a flying Bird, and code that calls fly() crashes. (b) A PdfReporter is forced to implement csvExport() and exportToXml() that it cannot meaningfully support. (c) A high-level DataHandler constructs its own FilesystemStorage, so every storage change ripples upward. (d) A reviewer objects that a variable holding a Java String violates "no variable should hold a reference to a concrete class". Is the reviewer right?

Step 1: match symptoms to the five statements

SRP: one reason to change. OCP: open for extension, closed for modification. LSP: subtypes substitutable for base types. ISP: clients not depending on methods they do not use. DIP: high-level and low-level both depend on abstractions.

Step 2: check (a) and (b) against the harm

(a) is about substituting subtypes. (b) is about methods the client does not use.

Step 3: check (c) and the reviewer's claim in (d)

(c) is dependency direction. (d) asks about the lecture's own "any exception?" question.

Full answer

(a) LSP: subtypes must be substitutable for their base types; any functionality expected from the base type should be fulfilled by the subtype. A penguin cannot fulfil fly(). The lecture's fix moves flying into a CanFly interface that Eagle has and Penguin does not, keeping Bird for what all birds share.

(b) ISP: many specialised interfaces are better than one universal; clients should not depend on methods they do not use. The universal export interface is polluted, and the PdfReporter's stub methods are the lecture's "smell of needless complexity". Split into small interfaces, one per real capability.

(c) DIP: high-level modules should not depend on low-level modules; both should depend on abstractions. The DataHandler's dependency is transitive: it is sensitive to changes all the way down, which is the lecture's stated problem. Fix: an abstract Storage interface, with FilesystemStorage as one detail that depends on it, and the storage injected into DataHandler. The lecture's test list: no variable holds a pointer to a concrete class, no class derives from a concrete class, no method overrides an implemented method of its base classes.

(d) The reviewer is wrong, and the lecture pre-empts the objection with its own "any exception? e.g. Java String". Stable, harmless value classes like String are the accepted exception; the rule targets references to concrete classes whose changes would ripple. This is the trap: treating a principle as a mechanical lint rule instead of a statement about change.

Reasoning chain: symptom → which statement it violates → the lecture's own fix shape → exceptions checked rather than assumed away.

Exercise 5 skill: mixed (from requirement to architecture to class structure) hard

This pulls in page 1 (cost of change) and page 2 (requirements). MediQueue must handle 10,000 concurrent users on results day, keep all patient data in one auditable store, and stay maintainable over a five-year life. (1) Which of the lecture's eight architectural design decisions is answered by this statement: "We will structure the system as one service per business area, each behind the same interface"? (2) The auditable-store requirement pushes which pattern, and what disadvantage is accepted? (3) In one service, class ExportService switches over an exportType field to produce PDFs and CSVs. Name the violation and the fix shape. (4) Using the page 1 cost facts, argue why the interface decision in (1) pays for itself.

Step 1: know the eight decisions

Generic architecture as template? Distribution across cores or processors? Patterns or styles? Fundamental approach to structuring the system? Decomposition into sub-components? Control strategy for component operation? Organisation best for delivering non-functional requirements? Documentation of the architecture?

Step 2: route (2) and (3) through the same chain as Exercises 2 and 3

Requirement → pattern and its disadvantage; code symptom → principle and fix.

Step 3: make the cost argument

Software costs more to maintain than to develop; long lives multiply that. Architecture refactoring is expensive because it affects many components.

Full answer

1. Decision 4: "What will be the fundamental approach used to structure the system?" The statement picks service-per-business-area behind a shared interface as the structuring approach. It is not yet the pattern (decision 3), the decomposition (decision 5), or the non-functional organisation (decision 7), though it will inform each of them.

2. Repository. All data in a central store, components interacting only through it, fits the auditable-store requirement and the pattern's "when used" (large volumes of information kept for a long time). Accepted disadvantages: the repository is a single point of failure (for a patient system, that is the one to take seriously), and organising all communication through it may be inefficient. The availability guidance answers the first: redundant components and fault tolerance around the store.

3. OCP violation: adding a format means modifying ExportService. Fix shape: a ReportFormat abstraction with PdfFormat and CsvFormat implementations, so a new format is new code. The lesson to carry into the service structure: each service's format variation lives behind its own interface, so the change cost stays local.

4. Page 1's cost fact: software costs more to maintain than to develop, and for long-lived systems maintenance may be several times development cost. MediQueue lives five years, and L5a adds that refactoring the architecture later is expensive because it affects so many components. A fixed interface per service keeps each year's changes inside one service instead of rippling across the system. That is money spent once at design time against rework spent every year, the same argument the lecture makes for designing the overall architecture early even in agile processes.

Reasoning chain: decision list matched to the statement → requirement to pattern with its disadvantage → code to principle with its fix → cost facts applied to the specific life span.

Discuss

Discuss

Take a position: "For a small team shipping one product, layered architecture is overhead: clean separation is hard to achieve anyway and every service request pays an interpretation cost. Ship a simpler structure and refactor if you survive." Defend or attack. Evidence that would change your mind: project histories showing what the later refactor actually cost versus the day-to-day cost of the layering; the lecture warns that architectural refactoring is expensive precisely because it touches so many components.
